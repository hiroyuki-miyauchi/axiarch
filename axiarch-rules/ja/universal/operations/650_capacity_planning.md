> [!IMPORTANT]

## §1. 主要方針・責務範囲 (Primary Directive & Scope)

### §1.1. 適用範囲

-   **Rule 650.1.1（適用対象）**: 本ファイルは、**本番トラフィックまたは本番データを扱う全システムの容量に関する事前計画活動**に適用する（MUST）。具体的には以下を含むが、これらに限定されない:
    -   スケール崖（線形にスケールしない限界）の列挙・台帳化・監視
    -   負荷試験による容量の実測較正と breaking point の特定
    -   ヘッドルーム方針・冗長性方針の策定
    -   オートスケールの上限・挙動・速度の統制
    -   需要予測（オーガニック / 非オーガニック）と容量調達のリードタイム管理
-   **判定基準**: 「このシステムは現在の何倍の負荷まで耐えるか？ 最初に壊れるのはどこか？」に**実測に基づいて**即答できないシステムは、本ファイルの未達状態にある。

-   **Rule 650.1.3（RFC 2119）**: 本ファイルの **MUST / MUST NOT / SHOULD / MAY** は RFC 2119 の定義に従う。MUST はリスク低減のための必須要件であり、逸脱には ADR による明示的な記録を要する。
-   **Rule 650.1.4（誇張禁止）**: 本ファイルは「容量起因の障害ゼロ」を約束しない。目的は**未知の崖を系統的に既知へ変換し、到達前のリードタイムを構造的に確保する**ことである。「無限にスケールする」「容量の心配は不要」といった表現は設計文書でも禁止する（MUST NOT）。

## §2. スケール崖の台帳化 (Scale Cliff Ledger)

> 本セクションが本ファイルの核である。「スケール崖（scale cliff）」とは、そこに到達するまで性能が概ね線形に保たれ、**到達した瞬間に非線形に劣化・停止する限界値**を指す。崖は台帳化されて初めて管理対象になる。

### §2.1. スケール崖の定義と列挙義務

-   **Rule 650.2.1（崖の列挙義務）**: 全システムは「線形にスケールしない限界」を列挙した**スケール崖台帳（Scale Cliff Ledger）**を維持しなければならない（MUST）。最低限、以下のカテゴリを検討対象とする:

| カテゴリ | 崖の例 | 到達時の典型的帰結 |
|:--------|:------|:-----------------|
| **DB 最大接続数** | PostgreSQL `max_connections`、マネージド DB のプラン上限 | 新規接続拒否 → アプリ全面エラー |
| **コネクションプール** | アプリ側プールサイズ、pooler（PgBouncer 等）の上限 | 接続待ちでレイテンシ急騰 → タイムアウト連鎖 |
| **ホットパーティション / ホットキー** | 特定パーティション・特定キーへのアクセス集中 | 全体容量に余裕があっても単一シャードが飽和 |
| **外部 API レート制限** | 決済・通知・LLM 等の per-second / per-day 上限 | 429 連発 → 機能停止または DLQ 滞留 |
| **クラウドサービスクォータ** | インスタンス数・IP 数・同時実行数・ストレージ API 上限 | スケールアウト自体が失敗する（§2.4） |
| **ファイルディスクリプタ** | プロセス / OS の FD 上限（ソケット含む） | accept 失敗・接続リーク時に突然死 |
| **単一リージョン容量** | 1 リージョンで調達可能なインスタンス・帯域の物理上限 | リージョン障害時のフェイルオーバー先に容量がない |

-   **Rule 650.2.2（暗黙の崖の禁止）**: 「設定した覚えのないデフォルト値」も崖である。DB 接続数・FD 上限・クラウドクォータの**デフォルト値を確認せずに本番運用してはならない**（MUST NOT）。デフォルトのまま採用する場合も、その値を台帳に記載し「意図的な採用」として記録する（MUST）。

### §2.2. 崖台帳の標準フィールド

-   **Rule 650.2.3（標準フィールド）**: 崖台帳の各エントリは、以下のフィールドを持たなければならない（MUST）:

| フィールド | 意味 |
|:----------|:-----|
| `id` / `name` | 崖の一意識別子と人間可読名 |
| `category` | §2.1 のカテゴリ分類 |
| `limit_value` | 限界値（数値 + 単位） |
| `limit_source` | 限界値の出典（設定ファイル / クラウドコンソール / 実測。「推定」の場合は明示） |
| `current_value_metric` | 現在値を取得するメトリクス（§2.3 の監視対象） |
| `ratio_warning` / `ratio_critical` | 比に対する警告 / 緊急閾値（例: 0.7 / 0.85） |
| `lead_time_days` | 到達前に確保すべきリードタイム（例: 30 日。緩和策の所要時間から逆算） |
| `mitigation` | 到達前の緩和策（上限引き上げ申請 / シャーディング / プール拡張等）と所要時間 |
| `behavior_at_limit` | 到達した場合に何が起きるか（実測または出典付き） |
| `owner` / `last_verified` | 担当者と最終検証日（§2.5） |

-   **Rule 650.2.4（limit_source の規律）**: `limit_source` が「推定」のままのエントリは未検証として扱い、§3 の実測較正の対象に積む（MUST）。推定値を検証済みのように扱ってはならない（MUST NOT）。

### §2.3. 現在値/限界値の比の監視とリードタイム付きアラート

-   **Rule 650.2.5（比の監視）**: 台帳の全エントリについて、**現在値 / 限界値の比**を継続的にメトリクスとして計上する（MUST）。絶対値の監視だけでは「限界までの距離」が読めない。
-   **Rule 650.2.6（リードタイム付きアラート）**: 比の閾値超過に加えて、**現在の成長率から限界到達日を推定し、`lead_time_days`（例: 30 日）を切った時点でアラート**する（MUST）。緩和策に 2 週間かかる崖を、到達 3 日前に知っても遅い。アラートの配信・通知設計は `operations/400` Part X へ委譲する。
-   **Rule 650.2.7（到達予測の前提明示）**: 到達日予測は線形外挿を最低限とし（MAY: 季節性を考慮したモデル）、**予測の前提（外挿期間・成長率の算出窓）をダッシュボード上に明示**する（SHOULD）。予測は §7 の需要予測イベント（キャンペーン等）と突き合わせて補正する（SHOULD）。

### §2.4. クラウドサービスクォータの統制

-   **Rule 650.2.8（クォータの台帳化）**: 利用中のクラウドサービスのクォータ（サービス上限）は、**アーキテクチャが依存する全項目を台帳に登録**する（MUST）。先行規範: AWS Well-Architected Reliability Pillar REL01「Manage service quotas and constraints」は、クォータの認知・監視・余裕確保を信頼性設計の最初の設問に置いている。
-   **Rule 650.2.9（クォータ監視の自動化）**: クォータの現在消費量と上限は、手動確認ではなく**自動取得・自動監視**する（SHOULD）。先行例: AWS Service Quotas API + 使用率アラーム、GCP Quota メトリクス。
-   **Rule 650.2.10（引き上げ申請のリードタイム）**: クォータ引き上げは**申請から適用まで日単位かかりうる**前提で、`lead_time_days` に申請所要時間を織り込む（MUST）。フェイルオーバー先リージョンのクォータも**平常時から本番相当に確保**しておく（MUST）— DR 発動時にクォータ申請から始める設計は不合格である。

### §2.5. 台帳の鮮度維持

-   **Rule 650.2.11（定期検証）**: 台帳の全エントリは定期的（四半期を上限の目安とする）に再検証し、`last_verified` を更新する（MUST）。限界値はプラン変更・インフラ更改・ライブラリ更新で**無断で動く**。
-   **Rule 650.2.12（変更時の台帳更新）**: アーキテクチャ変更（DB 移行・新外部 API 採用・リージョン追加等）の設計レビューでは、**崖台帳への追加・更新を完了条件に含める**（MUST）。

## §3. 容量の実測較正 (Empirical Capacity Calibration)

### §3.1. 伝統値の流用禁止

-   **Rule 650.3.1（伝統値の禁止）**: 「X 台で Y QPS 捌ける」という容量換算係数を、**過去の伝統値・他システムからの類推・口伝のまま流用してはならない**（MUST NOT）。先行規範: Google SRE Book は、コード・データ・トラフィックパターンの変化により容量係数が静かに陳腐化することを指摘し、負荷試験による定期較正を求めている。
-   **Rule 650.3.2（係数の出典管理）**: 容量換算係数（インスタンスあたり QPS、接続あたりメモリ等）は、**測定日・測定構成・測定シナリオ付きで記録**する（MUST）。出典のない係数は §2.4 の「推定」と同格に扱う。

### §3.2. Breaking Point Test（最初に飽和するリソースの特定）

-   **Rule 650.3.3（breaking point の特定）**: 負荷試験は目標値の合否判定だけでなく、**負荷を限界まで漸増させ「最初に飽和するリソース」を特定する breaking point test を含めなければならない**（MUST）。最初に飽和するのが CPU か、DB 接続か、外部 API か、FD かによって、緩和策はまったく異なる。
-   **Rule 650.3.4（崖台帳への還流）**: breaking point test で発見された限界は、**必ず §2 の崖台帳へ登録**する（MUST）。試験レポートに書いて終わりにしてはならない。
-   **Rule 650.3.5（劣化モードの記録）**: 限界到達時の**劣化の形**（レイテンシ急騰 / エラー率上昇 / 突然死 / 雪崩的連鎖）を記録する（SHOULD）。劣化モードは §8 の段階的劣化設計と `operations/400` のアラート設計の入力になる。

### §3.3. 較正の定期再実施

-   **Rule 650.3.6（定期再較正）**: 容量換算係数と breaking point は**定期的に再測定**する（MUST）。頻度はシステムの変化速度に応じて定めるが、メジャーなアーキテクチャ変更・依存更新・トラフィックパターン変化の後は必須とする。
-   **Rule 650.3.7（較正の自動化志向）**: 再較正は手動の一大イベントではなく、**再現可能なスクリプト・パイプラインとして自動化**することを推奨する（SHOULD）。自動化されていない較正は実施されなくなる。

## §4. ヘッドルーム方針 (Headroom Policy)

### §4.1. ヘッドルームの数値明文化

-   **Rule 650.4.1（ヘッドルームの明文化）**: 各システムは、**ピーク時に確保する余裕（ヘッドルーム）を数値で明文化**しなければならない（MUST）。例: 「予測ピークに対して 30–40% の余裕」または「N+1 / N+2」（§4.2）。明文化されていないヘッドルームは存在しないのと同じである。
-   **Rule 650.4.2（ヘッドルームの根拠）**: ヘッドルーム値は、**需要予測の誤差・スパイクの実績振れ幅・スケール所要時間（§6.3）**から根拠付けて設定する（SHOULD）。根拠なき一律値は、過剰（コスト浪費 — `operations/600`）にも過小（崖突入）にも倒れうる。
-   **Rule 650.4.3（ヘッドルームの監視）**: 実効ヘッドルーム（予測ピーク比の余裕）はダッシュボードで常時可視化し、方針値を割った場合は容量追加を起票する（MUST）。指標例は §10.3。

### §4.2. N+1 / N+2 冗長性

-   **Rule 650.4.4（N+2 の基準）**: 可用性が重要なサービスの容量は、**「計画停止（メンテナンス・デプロイ）と非計画停止（障害）が同時に発生しても残余容量でピークを処理できる」**ことを基準に設計する（SHOULD）。先行規範: Google SRE Book の N+2 プロビジョニング — 1 ユニットの計画停止中に 1 ユニットの非計画停止が起きても耐える。
-   **Rule 650.4.5（冗長性とヘッドルームの区別）**: N+1/N+2 は**ユニット喪失への耐性**、%ヘッドルームは**需要超過への耐性**であり、両者は代替関係にない（MUST: 両方を明示的に検討する）。
-   **Rule 650.4.6（フェイルオーバー先の容量）**: マルチリージョン / マルチ AZ 構成では、**フェイルオーバー先が残余トラフィックを受けられる容量（クォータ含む、§2.4）を平常時から確保**する（MUST）。フェイルオーバーは「経路の切替」ではなく「容量の引き受け」である。

## §5. 負荷試験の規律 (Load Testing Discipline)

> 負荷試験の実施環境制約（本番での負荷試験禁止）とツーリングは `operations/400` Part XVIII §46 を正本とする。本セクションは負荷試験を**容量計画の手段として成立させるための規律**を定義する。

### §5.1. 本番相当構成・本番相当データ分布

-   **Rule 650.5.1（本番相当構成）**: 容量較正に用いる負荷試験は、**本番相当の構成（インスタンスサイズ・レプリカ数・ネットワーク経路・設定値）**で実施する（MUST）。縮小環境での結果を線形換算して容量を主張してはならない（MUST NOT）— 崖は線形換算できないからこそ崖である。
-   **Rule 650.5.2（本番相当データ分布）**: 試験データは件数だけでなく**分布（カーディナリティ・ホットキーの偏り・レコードサイズ分布）**を本番相当にする（MUST）。一様分布の合成データはホットパーティションの崖（§2.1）を原理的に検出できない。PII を含む本番データの流用は `security/000` の統制に従う（MUST）。

### §5.2. 4 シナリオ（通常 / ピーク / スパイク / ソーク）

-   **Rule 650.5.3（4 シナリオ）**: 容量較正の負荷試験は、最低限以下の 4 シナリオを区別して実施する（MUST）:
    1.  **通常（average）**: 平常時相当の負荷での基準値取得
    2.  **ピーク（peak）**: 予測ピーク + ヘッドルーム分の持続負荷
    3.  **スパイク（spike）**: 短時間での急増（オートスケールの追従速度 §6.3 を検証）
    4.  **ソーク（soak）**: 長時間の持続負荷（リーク・FD 枯渇・ディスク逓増など**時間軸の崖**を検出）
-   **Rule 650.5.4（シナリオの省略禁止）**: スパイクとソークは「通常 / ピークで代替できる」ものではない（MUST NOT: 省略する場合は ADR で記録）。スパイクはスケール速度の崖を、ソークは資源リークの崖を、それぞれ唯一検出できるシナリオである。

### §5.3. リリース前の回帰負荷試験

-   **Rule 650.5.5（回帰負荷試験）**: 性能・容量に影響しうる変更（データアクセスパターン変更・依存追加・直列化形式変更等）は、リリース前に**回帰負荷試験**で容量係数の劣化を検証する（MUST）。判定基準は事前に定義した閾値（例: 容量係数の劣化が X% 以内）とし、超過時はリリースをブロックする（`operations/400` §46 の基準と整合させる）。
-   **Rule 650.5.6（劣化の累積管理）**: 単発では閾値内の小さな劣化も**累積を追跡**する（SHOULD）。リリースごとに 3% ずつ遅くなるシステムは、1 年で崖に到達する。

### §5.4. 既知イベント前の事前試験

-   **Rule 650.5.7（イベント前試験）**: フラッシュセール・キャンペーン・メディア露出・大型リリース等の**既知の需要イベントの前には、予測ピークに基づく事前負荷試験を実施**しなければならない（MUST）。崖台帳（§2）を参照し、イベントで踏み抜きうる崖（外部 API レート制限・クォータ）を事前点検する。
-   **Rule 650.5.8（イベント容量計画書）**: 大型イベントでは、予測ピーク・確保容量・踏み抜きうる崖と緩和策・当日の監視体制・段階的劣化の発動基準（§8）を 1 枚にまとめた**イベント容量計画**を作成する（SHOULD）。

## §6. オートスケール統制 (Autoscaling Governance)

### §6.1. 上限必須

-   **Rule 650.6.1（上限必須）**: オートスケールには**必ず上限（最大インスタンス数 / 最大同時実行数）を設定**する（MUST）。上限なしのオートスケールは、DDoS・バグ起因のリトライストーム・暴走ジョブをそのまま**請求額に変換する装置**である（コスト統制の正本は `operations/600`）。
-   **Rule 650.6.2（上限の根拠）**: 上限値は「コストの天井」と「下流の崖（DB 接続数等。スケールしても下流が先に飽和する点）」の両方から根拠付ける（MUST）。アプリ層だけ無限にスケールしても、DB 接続の崖が手前にあれば上限はそこである。

### §6.2. 上限到達時の挙動定義

-   **Rule 650.6.3（上限到達時の挙動）**: オートスケール上限に到達した場合の挙動を**事前に定義**しなければならない（MUST）。選択肢は load shedding（優先度の低いリクエストの拒否）・キューイング・段階的 degradation（§8）であり、「未定義（＝無差別タイムアウト）」を許容しない。レジリエンスパターン（load shedding / backpressure / circuit breaker）の実装詳細は `operations/400` Part XIX へ委譲する。
-   **Rule 650.6.4（上限到達の観測）**: 上限到達（および到達による拒否・劣化の発動）はメトリクス化し、アラート対象とする（MUST）。「上限で守られたこと」に気づけなければ、上限の見直し機会を失う。

### §6.3. スケール速度と崖（ウォームアップ時間）

-   **Rule 650.6.5（スケール速度の実測）**: 「スケール指示からトラフィック受け入れ可能になるまでの時間」（プロビジョニング + 起動 + ウォームアップ：JIT・キャッシュ・コネクション確立）を**実測して記録**する（MUST）。オートスケールは**ウォームアップ時間より速いスパイクに対しては存在しないのと同じ**である。
-   **Rule 650.6.6（スパイク対策の選択）**: ウォームアップ時間 > スパイク立ち上がり時間のシステムは、事前スケール（scheduled scaling）・常時ヘッドルーム（§4）・ウォームプールのいずれかを明示的に選択する（MUST）。スケールインの過剰な積極性がスパイク耐性を毀損していないかも点検する（SHOULD）。

## §7. 需要予測 (Demand Forecasting)

-   **Rule 650.7.1（2 系統の需要）**: 需要予測は**オーガニック需要（自然成長・季節性）と非オーガニック需要（キャンペーン・新機能ローンチ・メディア露出）を分離して管理**する（MUST）。先行規範: Google SRE Book の容量計画はこの 2 分法を基本に置く。オーガニックは外挿で予測できるが、非オーガニックは**計画情報の収集**でしか予測できない。
-   **Rule 650.7.2（定期更新）**: 需要予測は定期的（四半期を上限の目安とする）に更新し、**前回予測と実績の乖離を記録**する（MUST）。乖離の記録なき予測は精度が改善しない。
-   **Rule 650.7.3（非オーガニックの事前連絡経路）**: マーケティング・事業側のキャンペーン計画が**容量計画の担当へ事前に届く経路**を定義する（MUST）。崖を知らないままキャンペーンを実施することは §11 の最重要アンチパターンである。
-   **Rule 650.7.4（FinOps 接続）**: 需要予測は容量調達だけでなく**コスト予測の入力**として `operations/600` のプロセスと共有する（SHOULD）。容量計画とコスト計画が別々の数字を使う組織は、どちらかが必ず間違っている。

## §8. 段階的劣化の設計 (Graceful Degradation Design)

-   **Rule 650.8.1（劣化の事前設計）**: 崖への到達・容量超過時に**何をどの順で諦めるかを、平常時に設計**しておく（MUST）。過負荷の渦中で劣化順序を即興してはならない。
-   **Rule 650.8.2（優先度別シェディング）**: リクエスト / 機能を重要度で階層化し（例: 決済 > 閲覧 > レコメンド > 分析用イベント）、容量逼迫時は**低優先度から段階的にシェディング**する設計とする（MUST）。実装パターン（load shedding / circuit breaker / メンテナンスモード）は `operations/400` Part XIX・Part XXI へ委譲する。
-   **Rule 650.8.3（ユーザー影響の最小化）**: 劣化時のユーザー向け挙動（機能の非表示・簡易版表示・明示的な案内）は `design/000` の UX 原則に従って設計し、**無言のエラーや無限スピナーで劣化を表現してはならない**（MUST NOT）。
-   **Rule 650.8.4（劣化の発動・解除基準）**: 各劣化段階の発動条件と解除条件（ヒステリシス付き）を数値で定義し、可能なら自動発動とする（SHOULD）。手動発動の場合は権限者と手順を runbook 化する（MUST）。

## §9. テスト義務 (Testing Obligations)

> テスト層の定義・テスト環境の総論は `quality/000_qa_testing.md` を正本とする。本セクションは**崖シナリオ固有のテスト義務のみ**を定義する。

-   **Rule 650.9.1（崖シナリオ試験）**: 崖台帳（§2）の主要エントリについて、**実際に崖へ到達させた場合の挙動を非本番環境で試験**する（MUST）。最低限、以下のシナリオを含める:
    1.  **接続枯渇**: DB 接続 / コネクションプールを意図的に枯渇させ、待ち行列・タイムアウト・エラーの伝播を観測する
    2.  **クォータ / レート制限到達**: 外部 API・クラウドクォータの上限到達時に、リトライ規律（`engineering/700` §3.10）と劣化（§8）が設計通り動くことを検証する
    3.  **キャッシュ全損コールドスタート**: キャッシュが完全に失われた状態からの再始動で、オリジン（DB 等）が雪崩的負荷（cache stampede）に耐えるかを検証する（キャッシュ規律の正本は `engineering/730_caching_discipline.md`）
-   **Rule 650.9.2（劣化設計の試験）**: §8 の段階的劣化は、**発動・解除を含めて試験されていなければ設計と認めない**（MUST）。発動したことのない劣化機構は、本番で初めて動く未検証コードである。
-   **Rule 650.9.3（オートスケール挙動の試験）**: §6 の上限到達時挙動とスケール速度（ウォームアップ込み）は、スパイクシナリオ（§5.2）の負荷試験で検証する（MUST）。
-   **Rule 650.9.4（試験結果の還流）**: 崖シナリオ試験で得られた実際の挙動（`behavior_at_limit`）は崖台帳へ反映する（MUST）。

### §10.2. クォータ監視の擬似構成（§2.3, §2.4）

```text
# 擬似構成 — 台帳駆動のクォータ / 崖監視（特定ベンダ非依存）
for entry in scale_cliff_ledger:
    current = query_metric(entry.current_value_metric)     # 自動取得（Rule 650.2.9）
    ratio   = current / entry.limit_value
    emit_metric("capacity.cliff.ratio", value=ratio, labels={cliff_id: entry.id})

    growth_per_day = linear_regression(metric_history(entry, window=28d))
    if growth_per_day > 0:
        days_to_limit = (entry.limit_value - current) / growth_per_day
        emit_metric("capacity.cliff.days_to_limit", value=days_to_limit, labels={cliff_id: entry.id})

alert ratio        >= entry.ratio_warning       -> ticket（営業時間対応）
alert ratio        >= entry.ratio_critical      -> page（アラート配信は operations/400 Part X）
alert days_to_limit <= entry.lead_time_days     -> ticket（リードタイム警報 — Rule 650.2.6）
```

### §10.3. ヘッドルームダッシュボード指標（§4）

```text
# ヘッドルーム可視化の最小指標セット（Rule 650.4.3）
capacity.headroom.ratio        = (calibrated_capacity - forecast_peak) / calibrated_capacity
                                 # calibrated_capacity は §3 実測較正の出力。伝統値の使用禁止
capacity.cliff.ratio{cliff_id} = current / limit                    # 崖ごとの逼迫度（§10.2）
capacity.cliff.days_to_limit{cliff_id}                              # 到達予測（前提を注記表示 — Rule 650.2.7）
capacity.autoscale.at_max      = 1 if 現在インスタンス数 == 上限 else 0  # 上限到達の観測（Rule 650.6.4）
capacity.scaleup.seconds       = スケール指示 → サービスイン の実測時間（Rule 650.6.5）
capacity.forecast.error.ratio  = |実績ピーク - 予測ピーク| / 予測ピーク   # 予測精度の還流（Rule 650.7.2）
```

## §11. アンチパターン集 (Anti-Pattern Catalog)

| # | アンチパターン | 違反ルール | 帰結 |
|:--|:-------------|:----------|:-----|
| 1 | 伝統値（「昔測ったら X 台で Y QPS」）で容量を語る | 650.3.1 | 係数が陳腐化し、確保したつもりの容量が実在しない |
| 2 | クラウドクォータ・DB 接続数をデフォルト値のまま本番運用 | 650.2.2 | 「設定した覚えのない上限」に成長が衝突して全面障害 |
| 3 | オートスケールに上限を設定しない | 650.6.1 | DDoS・リトライストームが青天井の請求額に変換される |
| 4 | 負荷試験をリリース後（問題発生後）に初めて実施 | 650.5.5 | 容量劣化を本番ユーザーが最初に検出する |
| 5 | 崖台帳を持たずにキャンペーン・フラッシュセールを実施 | 650.5.7, 650.7.3 | 外部 API レート制限・クォータをイベント当日に踏み抜く |
| 6 | 縮小環境の負荷試験結果を線形換算して本番容量を主張 | 650.5.1 | 崖は線形換算できず、見積もりが崖の存在を隠す |
| 7 | 一様分布の合成データで負荷試験 | 650.5.2 | ホットパーティション / ホットキーの崖を検出できない |
| 8 | スパイク・ソークシナリオの省略 | 650.5.4 | スケール速度の崖・資源リークの崖が未検出のまま残る |
| 9 | 絶対値のみ監視し、現在値/限界値の比を監視しない | 650.2.5 | 「あと何割で崖か」が誰にも見えない |
| 10 | 比は監視するがリードタイム（到達予測）アラートがない | 650.2.6 | 緩和策の所要時間より遅く気づき、対策が間に合わない |
| 11 | フェイルオーバー先リージョンの容量・クォータを未確保 | 650.4.6, 650.2.10 | DR 発動時に「切替先に容量がない」ことが判明する |
| 12 | ウォームアップ時間を測らずオートスケールでスパイク対応を宣言 | 650.6.5–6 | スパイクの立ち上がりにスケールが間に合わず崖に到達 |
| 13 | 上限到達時の挙動が未定義（無差別タイムアウトに任せる） | 650.6.3 | 優先度の高い処理から無作為に死に、被害が最大化する |
| 14 | 段階的劣化を設計だけして一度も発動試験しない | 650.9.2 | 本番の過負荷時に劣化機構自体が初見のバグで動かない |
| 15 | breaking point test の発見を台帳に還流せず試験レポート止まり | 650.3.4 | 同じ崖を次のチームが本番で再発見する |

## §12. 成熟度モデル L1–L5 (Maturity Model)

| Level | 状態 | 特徴 |
|:------|:-----|:-----|
| **L1: Unaware** | 崖を知らない | 容量は「壊れたら増やす」。限界値の台帳なし。クォータ・接続数はデフォルトのまま |
| **L2: Reactive** | 飽和監視のみ | `operations/400` の飽和度監視はあるが、崖の列挙・限界値の出典管理・リードタイム予測がない |
| **L3: Ledgered** | 崖が台帳化されている | 崖台帳（§2）を維持し、現在値/限界値の比とリードタイムを監視。容量係数は実測較正（§3）済み |
| **L4: Disciplined** | 計画が規律化されている | ヘッドルーム方針（§4）明文化、4 シナリオ負荷試験（§5）・回帰負荷試験が定常運用。イベント前試験が必須手順 |
| **L5: Forecasted** | 予測駆動で運用されている | 需要予測（§7）と崖到達予測が定期更新され、予測誤差が還流。崖シナリオ試験（§9）と劣化発動試験が自動化されている |

-   **Rule 650.12.1（最低ライン）**: 本番トラフィックを受ける全システムは **L3 以上**を必須とする（MUST）。フラッシュセール等の大型需要イベントの実施は **L4 相当の手順**を満たしてから行う（MUST）。
