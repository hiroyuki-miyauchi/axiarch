# 740. データコントラクト & スキーマ進化 (Data Contracts & Schema Evolution)

> [!CAUTION]
> **このファイルは Universal Rule（不変ルール）です。「憲法改正」の明示的指示がない限り編集禁止。**
> 改定日: 2026-06-12

> [!IMPORTANT]
> **Level 1 Priority: Absolute Compliance（最上位の優先事項）**
> 組織・サービスの境界を越えて流れるデータは、変更の影響範囲が生産者の視界の外にある。スキーマの「小さな変更」が、別チームのパイプライン・別組織のレポート・数週間後のバッチを静かに破壊する。
> 本ファイルの MUST 要件はリスク低減と品質の底上げを目的とし、実装の簡便さ・開発速度よりも優先する。

> [!CAUTION]
> **Primary Directive（主要方針）**
> 「境界を越えて供給されるデータは API である。契約なき供給は、いつ破れるか誰も知らない口約束にすぎない」
> 本ファイルは、**組織 / サービス境界を越えるデータ（イベント・テーブル・トピック・ファイル）の生産者 / 消費者契約**を正本化する、言語・スタック非依存の横断規律である。
> リクエスト / レスポンス型の同期 API インターフェースは `engineering/100`（contract-first・versioning・Sunset）が正本であり、本ファイルは対象外とする（§1.2 責任分界表参照）。

## §1. 主要方針・責務範囲 (Primary Directive & Scope)

### §1.1. 適用範囲

-   **Rule 740.1.1（適用対象）**: 本ファイルは、**組織・チーム・サービスの境界を越えて供給される全データ資産**に適用する（MUST）。具体的には以下を含むが、これらに限定されない:
    -   イベントストリーム（メッセージキュー・イベントバスのトピック）
    -   共有テーブル / ビュー（他チームが読む DB テーブル・DWH テーブル）
    -   エクスポート / 取込ファイル（CSV・JSON Lines・Parquet 等の定期受け渡し）
    -   分析基盤への供給（DWH / Lakehouse / レポーティング基盤へ流れるデータセット）
-   **判定基準**: 「このデータの形・意味・鮮度が変わったとき、自分のチームの外で誰かが壊れるか？」— Yes なら本ファイルの適用対象である。チーム内部に閉じた中間データは対象外（MAY）だが、後から境界を越えた時点で契約義務が発生する。

### §1.3. 基本原則と RFC 2119 用語

-   **Rule 740.1.3（RFC 2119）**: 本ファイルの **MUST / MUST NOT / SHOULD / MAY** は RFC 2119 の定義に従う。MUST はリスク低減のための必須要件であり、逸脱には ADR による明示的な記録を要する。
-   **Rule 740.1.4（誇張禁止）**: 本ファイルは「スキーマが壊れない」ことを約束しない。目的は**破壊を予見可能にし、移行のコストとリスクを系統的に下げる**ことである。「後方互換を完全保証」「破壊的変更ゼロ」といった表現は設計文書でも禁止する（MUST NOT）。
-   **Rule 740.1.5（契約なくして供給なし）**: §2 の構成要素を満たす契約が存在しないデータ資産を、新規に組織 / サービス境界を越えて供給してはならない（MUST NOT）。既存の契約なし供給は §11 の成熟度評価に基づき計画的に契約化する（SHOULD）。

## §2. 契約の構成要素 (Contract Components)

> 本セクションが本ファイルの核である。契約とは「スキーマファイル」ではなく、**スキーマ + 責任 + 品質保証 + 利用文脈**の束である。

### §2.1. 必須構成要素

-   **Rule 740.2.1（必須構成要素）**: 全データ契約は、最低限以下の構成要素を含まなければならない（MUST）:

| 構成要素 | 内容 |
|:--------|:-----|
| **スキーマ** | フィールド名・型・必須性・enum 値域・**セマンティクス**（単位・タイムゾーン・ID 体系・null の意味） |
| **オーナー（生産者）** | 責任チーム名 + 連絡可能な窓口（§2.4）。個人名のみは不可 |
| **SLA** | 鮮度（freshness）・完全性（completeness）の**数値**目標（§6） |
| **品質ルール** | 一意性・null 率・値域・参照整合性などの検証可能なルール |
| **利用目的・分類** | データの想定用途、フィールド単位のデータ分類タグ（PII / 機密 / 公開、§7） |
| **互換性モード** | BACKWARD / FORWARD / FULL（+ transitive）の明示選択（§3.1） |
| **バージョン** | 契約自体のバージョンと変更履歴 |

-   **判定基準**: 「初めてこのデータを消費するチームが、生産者に一度も質問せずに安全な消費者を実装できるか？」— できなければ契約は不完全である。

### §2.2. 契約はコードとして Git 管理

-   **Rule 740.2.2（契約はコード）**: 契約は機械可読フォーマット（YAML / JSON / IDL）で記述し、**Git で管理し、変更はレビューを経由し、CI で検証**する（MUST）。wiki・スプレッドシート・口頭合意による契約管理を禁止する（MUST NOT）。
-   **Rule 740.2.3（CI 検証の内容）**: 契約リポジトリの CI は最低限、①契約フォーマット自体の妥当性検証、②互換性チェック（§3）、③必須構成要素（§2.1）の充足確認を自動実行する（MUST）。
-   **先行例**: GoCardless の data contracts — 契約を Git 管理の宣言的定義とし、CI 検証を通じてスキーマ・基盤リソースの生成まで契約から駆動する。契約が「ドキュメント」ではなく「実行されるコード」になった代表事例である。

### §2.3. 参照標準 — ODCS（新興標準）

-   **Rule 740.2.4（参照標準）**: 契約フォーマットの設計には **ODCS（Open Data Contract Standard）** を参照標準として用いることを推奨する（SHOULD）。ODCS は Linux Foundation AI & Data 傘下の **Bitol** プロジェクトが策定する**新興・進行中の標準**であり、2025年12月に v3.1.0 が公開されている。PayPal が公開した Data Contract Template を起源とする。
-   **位置づけの正確な理解**: ODCS は確立された普遍標準ではなく、進化中の標準である。全面採用を強制しない（MAY）。自前フォーマットでも §2.1 の構成要素を満たせば本ファイルに適合する。ただし新規に契約フォーマットを設計する場合、ODCS の語彙（schema / quality / slaProperties / team 等）に整合させておくことで、将来のツール連携コストを下げられる。
-   **簡略例**: §9.1 参照。

### §2.4. オーナー不在の契約禁止

-   **Rule 740.2.5（オーナー必須）**: 契約のオーナーは**チーム単位**で定義し、連絡可能な窓口（チームチャンネル・メーリングリスト・オンコール）を併記する（MUST）。退職・異動で連絡不能になる個人名のみのオーナー表記を禁止する（MUST NOT）。
-   **Rule 740.2.6（ownerless data の禁止）**: オーナー不明のデータ資産への新規依存を追加してはならない（MUST NOT）。発見した場合はオーナー確定（または計画的廃止）を起票する（SHOULD）。

## §3. 互換性モード (Compatibility Modes)

### §3.1. 互換性モードの明示選択

-   **Rule 740.3.1（明示選択）**: 全データ資産は、互換性モードを以下から**明示的に選択し、契約に記載**する（MUST）。「未設定（暗黙の挙動）」を禁止する（MUST NOT）:

| モード | 意味 | 先に更新する側 | 許可される主な変更 |
|:------|:-----|:-------------|:------------------|
| **BACKWARD** | 新スキーマの消費者が、旧スキーマで書かれたデータを読める | 消費者 | フィールド削除、optional フィールド追加 |
| **FORWARD** | 旧スキーマの消費者が、新スキーマで書かれたデータを読める | 生産者 | フィールド追加、optional フィールド削除 |
| **FULL** | BACKWARD と FORWARD の両方 | どちらでも可 | optional フィールドの追加・削除のみ |
| **\*_TRANSITIVE** | 直前バージョンだけでなく**全過去バージョン**との互換を要求 | 上記に同じ | 上記より厳格 |

-   **先行例**: Confluent Schema Registry の compatibility modes。上表は同レジストリの定義に整合させており、Avro / Protobuf / JSON Schema いずれでも同型の判定が適用される。

### §3.2. 既定は BACKWARD

-   **Rule 740.3.2（既定 BACKWARD）**: 明示的な理由がない限り、既定は **BACKWARD** とする（SHOULD）。BACKWARD は「消費者を先に更新すれば生産者のスキーマ進化が消費者を壊さない」運用を可能にし、Confluent Schema Registry の既定値でもある。
-   **Rule 740.3.3（FULL の盲目選択禁止）**: FULL / FULL_TRANSITIVE は最も安全に見えるが、許可される変更が最も狭く、**スキーマ進化を事実上停止させる**副作用を持つ。トレードオフを評価せずに盲目的に選択してはならない（MUST NOT）。選択する場合は理由を契約に記録する（MUST）。

### §3.3. transitive モードの適用判断

-   **Rule 740.3.4（transitive の適用）**: 過去データの**再処理・リプレイ**が想定される資産（長期保存トピック・イベントソーシング・バックフィル対象）は、`*_TRANSITIVE` を選択する（SHOULD）。直前バージョンとの互換だけでは、古いデータを新コードで読む際に破綻する。

### §3.4. スキーマレジストリ（単一参照点）必須

-   **Rule 740.3.5（単一参照点）**: 境界を越える全スキーマは、**スキーマレジストリまたは同等の単一参照点**に登録する（MUST）。「同等の単一参照点」とは、全生産者・全消費者が同一のスキーマ定義を参照でき、互換性チェックを機械実行できる場所を指す（専用レジストリ製品のほか、契約リポジトリ + CI でも要件を満たせる）。
-   **判定基準**: 「いまこのトピック / テーブルの正しいスキーマはどれか？」に、コードを読まずに単一の場所で即答できるか。

### §3.5. 未登録スキーマの生産ブロック

-   **Rule 740.3.6（未登録の生産ブロック）**: レジストリに未登録（または互換性チェック未通過）のスキーマによるデータ生産を、**CI（デプロイ前）またはランタイム（直列化時）でブロック**する（MUST）。「登録は後で」を許すと、レジストリは現実と乖離した飾りになる。
-   **実装指針**: ランタイムブロックが可能な基盤（レジストリ統合シリアライザ等）ではランタイムを第一とし、ファイル受け渡し等ランタイム検証が困難な経路では CI + 受信側検証（§5.3）で代替する（SHOULD）。

## §4. 破壊的変更の定義と手順 (Breaking Changes: Definition & Procedure)

### §4.1. 破壊的変更の列挙

-   **Rule 740.4.1（破壊的変更の定義）**: 以下の変更は、互換性モードの判定結果にかかわらず**破壊的変更として扱う**（MUST）:
    -   フィールドの削除
    -   フィールドの型変更（widening を含め、消費者の検証が通らなくなりうる変更）
    -   optional → required への変更（必須化）
    -   enum 値域の削除・縮小
    -   フィールド名の変更（削除 + 追加と等価）
    -   **セマンティクス変更**: 型・名前が不変でも、単位（円 → ドル）・タイムゾーン・ID 体系・null の意味が変わる変更。**スキーマチェッカーはセマンティクス変更を検出できない**ため、人間のレビューで明示的に判定する（MUST）
    -   キー・パーティショニング・一意性保証の変更
-   **Rule 740.4.2（追加的変更）**: optional フィールドの追加・enum 値域の拡大は原則として非破壊だが、enum 拡大は消費者側の未知値処理（§5.1）が前提である。契約に消費者規律が明記されていない資産では、enum 拡大も破壊的変更として扱う（SHOULD）。

### §4.2. 3段階移行手順（並行配信 → 移行確認 → 旧版廃止）

-   **Rule 740.4.3（3段階手順）**: 破壊的変更は以下の3段階で実施し、段階の省略・順序逆転を禁止する（MUST）:
    1.  **新バージョン並行配信**: 新スキーマを**別バージョン（別トピック / 別テーブル / バージョンフィールド）として旧版と並行配信**する。移行期限を契約に明記する
    2.  **消費者移行確認**: 消費者台帳（§4.4）とアクセスログにより、**全消費者の新版移行を確認**する
    3.  **旧版廃止**: 消費者ゼロを確認した後にのみ、旧版の配信停止・削除を行う
-   **Rule 740.4.4（消費者ゼロ確認まで削除禁止）**: 旧版の消費者がゼロであることを確認するまで、旧版を削除・停止してはならない（MUST NOT）。「お知らせを出したから削除してよい」は許可されない。お知らせは手順の代替ではなく前提にすぎない。

### §4.3. Deprecation 規律（Sunset 整合）

-   **Rule 740.4.5（期限付き deprecation）**: 旧版の非推奨化は、**廃止予定日を明示**して通知する（MUST）。「いつか移行してください」という期限なし deprecation を禁止する（MUST NOT）。
-   **整合**: 同期 API の Deprecation / Sunset ヘッダー規律は `engineering/100` §6.3 を正本とする。データ資産では同じ思想を契約フィールド（deprecation 日付 + 廃止日付）として表現する。

### §4.4. 消費者台帳

-   **Rule 740.4.6（消費者の把握）**: 契約された各データ資産について、**誰が消費しているかを把握する手段**（消費者登録制またはアクセスログによる検出）を持つ（MUST）。消費者を把握できない資産に破壊的変更を加えてはならない（MUST NOT）。
-   **判定基準**: 「この資産を止めたら、何件のシステムが壊れるか？」に数値で答えられるか。

## §5. 消費者側規律 (Consumer-Side Discipline)

> 契約は生産者だけの義務ではない。壊れにくいデータエコシステムの半分は、消費者の読み方の規律で決まる。

### §5.1. Tolerant Reader

-   **Rule 740.5.1（未知フィールドの無視）**: 消費者は**未知フィールドを無視**し、自分が必要とするフィールドのみを取り出す Tolerant Reader として実装する（MUST）。未知フィールドの存在でエラーを送出する厳格パースは、生産者の非破壊的進化（フィールド追加）を破壊的に変えてしまう。
-   **Rule 740.5.2（未知 enum 値の安全な処理）**: enum を消費するコードは、**未知の値に対する明示的なフォールバック**（`unknown` 扱い・スキップ + 計数）を実装する（MUST）。未知 enum 値でのクラッシュは enum 拡大（§4.2）を不可能にする。
-   **先行例**: Tolerant Reader パターン（Martin Fowler）。

### §5.2. 契約テスト

-   **Rule 740.5.3（依存フィールドの宣言）**: 消費者は、自分が依存するフィールド・型・値域を**契約テストとして宣言**する（SHOULD）。これにより生産者は「何を変えると誰が壊れるか」を CI で機械的に知ることができる。
-   **委譲**: 契約テストのツール（Pact 等）・Broker 運用・実施層の定義は `quality/000` §7 を正本とする。本条は「データ資産の消費者も契約テストの対象である」ことのみを定める。

### §5.3. スキーマ検証の失敗時挙動（DLQ）

-   **Rule 740.5.4（違反データの計数 + DLQ）**: 受信データの契約検証（スキーマ・品質ルール）に失敗した item は、**黙って捨てず、計数のうえ元ペイロードとともに DLQ へ退避**する（MUST）。計数・退避・監視の規律は `engineering/700` §2.4（per-item 失敗捕捉と DLQ）と同一であり、契約違反は失敗分類タクソノミ上の `user.non_retryable` 系として計上する（SHOULD）。
-   **Rule 740.5.5（違反の生産者への還流）**: 契約違反の検出は消費者側で完結させず、**生産者へ通知・還流**する仕組みを持つ（SHOULD）。消費者側の防御だけでは、違反データは供給され続ける。

### §5.4. 契約外依存の禁止

-   **Rule 740.5.6（契約外依存の禁止）**: 契約に記載のないフィールド・内部実装テーブルへの直接依存（他チーム DB への直接 SELECT 等）を禁止する（MUST NOT）。契約外依存は生産者の視界に入らないため、§4 の手順による保護を一切受けられない。
-   **実装指針**: 生産者は内部テーブルと公開インターフェース（契約された外部スキーマ）を分離し、内部への直接アクセスを権限で遮断する（SHOULD）。

---

## §6. SLA とデータ品質 (SLA & Data Quality)

-   **Rule 740.6.1（数値 SLA 必須）**: 契約の SLA は、最低限**鮮度**（例: イベント発生から利用可能まで 15 分以内）と**完全性**（例: 対象レコードの 99.9% 以上が到達）を**数値で**定義する（MUST）。「ベストエフォート」「なるべく早く」といった非数値 SLA を禁止する（MUST NOT）。
-   **Rule 740.6.2（計測義務）**: SLA は計測されて初めて契約として機能する。鮮度・完全性は**メトリクスとして継続計測**し、契約値との乖離を可視化する（MUST）。新旧・上流下流の突合（リコンシリエーション）の手法は `engineering/710` を、メトリクス基盤・品質スコアの総論は `ai/100` を正本とする。
-   **Rule 740.6.3（SLA 違反の通知）**: SLA 違反は**生産者が自ら検知し、消費者へ通知**する（MUST）。消費者が「データが来ない」ことに先に気づく状態は、契約の責任配置が逆転している。アラート設計は `operations/400` へ委譲する。
-   **Rule 740.6.4（品質ルールの実行）**: 契約に記載した品質ルール（一意性・null 率・値域）は、文書ではなく**パイプライン上で実行される検証**として実装する（MUST）。実行されないルールは存在しないルールである。

---

## §7. PII / 分類タグ (PII & Classification Tags)

-   **Rule 740.7.1（分類タグ必須）**: 契約は**フィールド単位のデータ分類タグ**（例: PII / 機密 / 内部 / 公開）を必須記載とする（MUST）。タグなしフィールドを含むデータ資産を境界を越えて供給してはならない（MUST NOT）。分類タクソノミの正本は `security/100` とする。
-   **Rule 740.7.2（マスキング義務の伝播）**: 下流の消費者・再供給者は、契約の分類タグに基づく**マスキング・アクセス制御・保持期間の義務を継承**する（MUST）。分類タグは「最初の供給点で付与し、下流へ伝播する」ことで、データが何段転送されても統制が追従する。
-   **Rule 740.7.3（分類変更は破壊的変更扱い）**: フィールドの分類変更（特に非 PII → PII への変更）は、消費者側の取り扱い義務を変えるため**破壊的変更として §4 の手順で扱う**（MUST）。
-   **Rule 740.7.4（後付けタグの禁止）**: 「供給を開始してから分類タグを付ける」運用を禁止する（MUST NOT）。タグなし期間に複製されたデータは統制不能になる。

## §8. テスト義務 (Testing Obligations)

> テスト層の定義・契約テストツールの総論は `quality/000` を正本とする。本セクションは**データ契約固有のテスト義務のみ**を定義する。

-   **Rule 740.8.1（互換性 CI テスト）**: スキーマ・契約を変更する全 PR で、**レジストリ（§3.4）に対する互換性チェックを自動実行**し、選択された互換性モード（§3.1）への違反をブロックする（MUST）。互換性判定を人間のレビューのみに依存してはならない（MUST NOT）。
-   **Rule 740.8.2（契約違反検出テスト）**: 契約違反データ（型不一致・必須欠落・値域逸脱）を意図的に注入し、以下を検証する（MUST）:
    -   違反が検出され、正しく計数される
    -   違反 item が DLQ へ退避される（§5.3）
    -   正常 item の処理が違反 item に巻き込まれない
-   **Rule 740.8.3（消費者の Tolerant Reader テスト）**: 消費者は、**未知フィールドを含む入力**と**未知 enum 値を含む入力**で正常動作することを検証するテストを持つ（MUST）。
-   **Rule 740.8.4（品質ルール実行のテスト）**: 契約の品質ルール（§6.4）がパイプライン上で実際に実行され、違反時に検知されること自体をテストで検証する（SHOULD）。

### §9.1. 契約 YAML 例（ODCS 風・簡略）

```yaml
# data-contract.yaml — ODCS（v3.1.0）の語彙に整合させた簡略例
# 注: ODCS は新興・進行中の標準。完全準拠ではなく §2.1 構成要素の充足が要件
apiVersion: v3.1.0
kind: DataContract

status: active
domain: commerce
team:
  - role: owner
    name: commerce-platform-team        # チーム単位（Rule 740.2.5）
    channel: "#commerce-platform"       # 連絡可能な窓口
description:
  purpose: 注文完了イベント。会計集計・在庫同期・分析基盤への供給に使用
compatibility: BACKWARD_TRANSITIVE      # §3.1 明示選択（リプレイありのため transitive）
schema:
  - name: order_completed
    properties:
      - name: order_id
        logicalType: string
        required: true
        primaryKey: true
        classification: internal        # §7 分類タグ（フィールド単位）
      - name: customer_email
        logicalType: string
        required: true
        classification: pii             # 下流にマスキング義務が伝播
      - name: amount
        logicalType: integer
        required: true
        classification: internal
        description: "金額。単位は JPY（セマンティクスを契約に明記）"
      - name: status
        logicalType: string
        required: true
        classification: public
        # enum 拡大可。消費者は未知値フォールバック必須（Rule 740.5.2）
        allowedValues: [completed, refunded, partially_refunded]
quality:
  - rule: uniqueness
    property: order_id
  - rule: nullRate
    property: customer_email
    mustBeLessThan: 0.001
slaProperties:
  - property: freshness          # §6 数値 SLA
    value: 15
    unit: minutes
  - property: completeness
    value: 99.9
    unit: percent
deprecation: null                # 非推奨化時は date + sunsetDate を必須記載（§4.3）
```

### §9.2. 互換性チェック CI の擬似構成（§8.1）

```yaml
# .ci/contract-check.yaml — 契約リポジトリ / スキーマ変更 PR で実行する擬似構成
on: pull_request

jobs:
  contract-validation:
    steps:
      - name: 契約フォーマット検証          # Rule 740.2.3 ①
        run: contract-cli validate ./contracts/**/*.yaml
      - name: 必須構成要素の充足確認        # Rule 740.2.3 ③ — owner / SLA / 分類タグ
        run: contract-cli lint --require owner,sla,classification
      - name: 互換性チェック               # Rule 740.8.1 — レジストリの現行版と比較
        run: |
          schema-registry-cli test-compatibility \
            --subject commerce.order_completed \
            --mode-from-contract \
            --schema ./contracts/commerce/order_completed.yaml
        # 選択モード（例: BACKWARD_TRANSITIVE）違反なら exit 非0 で PR をブロック
      - name: 破壊的変更のセマンティクスレビュー要求
        # 型チェッカーはセマンティクス変更を検出できない（Rule 740.4.1）
        # description / 単位 / classification の差分があれば人間レビューを必須化
        run: contract-cli diff --require-human-review-on semantics,classification
```

### §9.3. Tolerant Reader 例（e.g. TypeScript）

```typescript
// §5.1 Tolerant Reader の参考実装 — 必要フィールドのみ検証して取り出す
type OrderStatus = 'completed' | 'refunded' | 'partially_refunded';

interface OrderCompletedV2 {
  orderId: string;
  amountJpy: number;
  status: OrderStatus | 'unknown'; // 未知 enum 値は 'unknown' に正規化（Rule 740.5.2）
}

function readOrderCompleted(raw: unknown): OrderCompletedV2 {
  const r = raw as Record<string, unknown>;
  // 依存するフィールドのみ検証する。未知フィールドは検査せず無視（Rule 740.5.1）
  if (typeof r.order_id !== 'string' || typeof r.amount !== 'number') {
    // 契約違反: 黙って捨てず、計数のうえ DLQ へ（Rule 740.5.4 / 700 §2.4）
    throw new ContractViolationError('order_completed', r.order_id);
  }
  const known: ReadonlyArray<OrderStatus> = ['completed', 'refunded', 'partially_refunded'];
  const status = known.includes(r.status as OrderStatus)
    ? (r.status as OrderStatus)
    : 'unknown'; // enum 拡大に耐える。'unknown' の件数は計数して可視化する
  return { orderId: r.order_id, amountJpy: r.amount, status };
}
```

## §10. アンチパターン集 (Anti-Pattern Catalog)

| # | アンチパターン | 違反ルール | 帰結 |
|:--|:-------------|:----------|:-----|
| 1 | レジストリ・単一参照点なしでスキーマを生産する | 740.3.5–6 | 「正しいスキーマ」が存在せず、生産者ごとに微妙に違うデータが流れる |
| 2 | FULL / FULL_TRANSITIVE を盲目選択して進化停止 | 740.3.3 | ほぼ全変更が互換性違反になり、回避のため契約外の別経路が増殖する |
| 3 | 破壊的変更を「お知らせのみ」で断行する | 740.4.3–4 | 通知を見ていない消費者が本番で壊れる。告知は手順の代替にならない |
| 4 | 消費者数を把握せずフィールド・旧版を削除する | 740.4.6 | 削除した瞬間に未知の依存システムが連鎖故障する |
| 5 | PII 無タグのデータ供給 | 740.7.1–2 | 下流がマスキング義務を知らないまま複製・転送し、統制不能になる |
| 6 | 契約を wiki / スプレッドシート / 口頭合意で管理する | 740.2.2 | 契約と現実が乖離し、誰もどちらが正かを判定できない |
| 7 | オーナーが個人名のみ・または不明のデータ資産 | 740.2.5–6 | 異動・退職で「触ってよいか誰にも聞けないデータ」が誕生する |
| 8 | SLA を「ベストエフォート」と記載する | 740.6.1 | 鮮度遅延・欠損が起きても違反と判定できず、改善が永遠に始まらない |
| 9 | 消費者が他チームの内部テーブルを直接 SELECT する | 740.5.6 | 生産者のリファクタリングが未知の他チームを破壊する |
| 10 | 未知フィールドの存在で消費者がエラーを送出する | 740.5.1 | 生産者の非破壊的なフィールド追加が破壊的変更に化ける |
| 11 | 契約違反データを黙ってドロップする（計数なし） | 740.5.4 | データ欠損が静かに進行し、集計のズレとして数週間後に発覚する |
| 12 | 型が同じだからとセマンティクス変更（単位・TZ）を非破壊扱い | 740.4.1 | スキーマチェックを素通りし、数値が壊れたまま下流へ流れ続ける |
| 13 | 期限なし deprecation（「いつか移行してください」） | 740.4.5 | 旧版が永久に残り、二重メンテナンスが恒久化する |
| 14 | 互換性チェックを人間レビューのみに依存する | 740.8.1 | レビュアーの見落とし1回で互換性が破れる。機械化可能な判定を人に頼らない |
| 15 | 供給開始後に分類タグを後付けする運用 | 740.7.4 | タグなし期間に複製されたデータが統制の外に残り続ける |

## §11. 成熟度モデル L1–L5 (Maturity Model)

| Level | 状態 | 特徴 |
|:------|:-----|:-----|
| **L1: Implicit** | 契約が存在しない | スキーマはコードの中にのみ存在。他チームは DB 直読・リバースエンジニアリングで消費。破壊は事後発覚 |
| **L2: Documented** | 文書はあるが強制がない | wiki にスキーマ表がある。現実と乖離し、互換性チェック・SLA 計測はない |
| **L3: Contracted** | 契約がコード化されている | 契約は Git 管理 + 必須構成要素（§2.1）充足。レジストリ + CI 互換性チェックが機能している |
| **L4: Enforced** | 契約が実行時に強制される | 未登録スキーマの生産ブロック・違反データの DLQ・SLA の継続計測 + 違反通知が機能。破壊的変更は3段階手順が既定 |
| **L5: Federated** | 組織標準として自走する | 標準フォーマット（ODCS 等）に統一。消費者台帳・影響分析が自動化され、契約変更の影響範囲がセルフサービスで分かる |

-   **Rule 740.11.1（最低ライン）**: 組織 / サービス境界を越えて供給する全データ資産は **L3 以上**を必須とする（MUST）。PII を含む資産の供給は **L4 相当の強制機構**を満たしてから行う（MUST）。
