# 710. データ整合・リコンシリエーション (Data Reconciliation & Invariants)

> [!CAUTION]
> **このファイルは Universal Rule（不変ルール）です。「憲法改正」の明示的指示がない限り編集禁止。**
> 改定日: 2026-06-12

> [!IMPORTANT]
> **Level 1 Priority: Absolute Compliance（最上位の優先事項）**
> 金銭・在庫・ポイントのような「保存則が成り立つ量」の不整合は、発生した瞬間ではなく**数週間後の請求・決算・ユーザー問い合わせ**で発覚する、最も静かで最も高価なデータ欠陥である。

> [!CAUTION]
> **Primary Directive（主要方針）**
> 「検証されていない整合性は、存在しない整合性と区別できない」
> 本ファイルは、保存則が成り立つ量（金銭・在庫・ポイント・クレジット・利用量課金・件数）を扱う**全システム**に適用される、言語・スタック非依存の普遍規律である。

## §1. 主要方針・責務範囲 (Primary Directive & Scope)

### §1.1. 適用範囲 — 保存則が成り立つ量

-   **Rule 710.1.1（適用対象）**: 本ファイルは、**保存則が成り立つ量（conserved quantity）を保持・集計・転送する全システム**に適用する（MUST）。具体的には以下を含むが、これらに限定されない:
    -   金銭（残高・売上・手数料・返金・払い出し）
    -   在庫（入庫・出庫・引当・棚卸）
    -   ポイント / クレジット（発行・消費・失効・残高）
    -   無料枠・クォータ（付与・消費・残量・リセット）
    -   利用量課金（メータリングイベント・集計値・請求明細）
    -   件数（上流レコード数・イベント数・出力行数の対応関係）
-   **判定基準**: 「この量は、どこかが増えたら、どこかが減る（または増分の由来を説明できる）べきか？」に Yes と答える量は、すべて本ファイルの適用対象である。生成・消滅が自由なキャッシュ的データ（再計算可能な派生値そのもの）は対象外だが、**派生値と原本の対応関係**は §3.3 の突合対象である。

### §1.3. 基本原則と RFC 2119 用語

-   **Rule 710.1.3（RFC 2119）**: 本ファイルの **MUST / MUST NOT / SHOULD / MAY** は RFC 2119 の定義に従う。MUST はリスク低減のための必須要件であり、逸脱には ADR による明示的な記録を要する。
-   **Rule 710.1.4（誇張禁止）**: 本ファイルは「不整合ゼロ」を約束しない。目的は**差異の検知を構造化し、説明可能性を高め、未説明差異の滞留時間を系統的に短くする**ことである。「完全な整合性を保証」「差異が絶対に発生しない設計」といった表現は設計文書でも禁止する（MUST NOT）。
-   **Rule 710.1.5（検証なくして信頼なし）**: 不変量（§2）と定常突合（§3）を持たない保存則量を、請求・決算・在庫引当などの**意思決定に直接使用してはならない**（MUST NOT）。例外は §12 成熟度 L1 から計画的に引き上げる移行期間中のみとし、ADR に記録する（MAY）。

## §2. 不変量（Invariant）の明文化 (Explicit Invariants)

> 本セクションが本ファイルの核である。不変量とは「システムが正しいかぎり、いつ評価しても必ず成り立つ等式・不等式」であり、リコンシリエーション（§3）はこの不変量を定常的に評価する行為である。

### §2.1. 不変量定義の義務

-   **Rule 710.2.1（不変量定義義務）**: 保存則が成り立つ量（§1.1）には、**必ず 1 つ以上の不変量を明文化**しなければならない（MUST）。不変量のない保存則量は「正しさの定義がないまま運用されている量」である。
-   **Rule 710.2.2（実行可能性）**: 不変量は散文ではなく、**機械的に評価可能な形式**（SQL・クエリ・コード）で定義する（MUST）。「概ね一致するはず」のような評価不能な記述は不変量とみなさない。
-   **Rule 710.2.3（双方向の導出）**: 不変量は可能なかぎり**独立した 2 経路からの導出値の一致**として定義する（SHOULD）。同一テーブルの同一カラムを 2 回読む検証は、書き込みバグを原理的に検出できない（`engineering/700` Rule 700.3.13 検証の独立と同根の原則）。
-   **Rule 710.2.4（粒度の二層）**: 不変量は**グローバル集約（全体合計）とエンティティ単位（口座・SKU・テナント単位）の二層**で定義する（SHOULD）。グローバル合計のみの検証は、+100 と −100 のように相殺し合う差異を構造的に見逃す。
-   **判定基準**: 「この量が間違っているとき、どのクエリを実行すれば間違いだと証明できるか？」に即答できなければ、不変量は未定義である。

### §2.2. 不変量カタログの維持

-   **Rule 710.2.5（カタログ必須）**: プロジェクトは**不変量カタログ**（バージョン管理されたドキュメントまたは定義ファイル）を維持する（MUST）。各エントリは最低限以下を含む:

| フィールド | 内容 |
|:----------|:-----|
| `invariantId` | 安定した一意 ID（例: `INV-LEDGER-001`） |
| 対象量 / テーブル | どの保存則量・どのストレージを検証するか |
| 定義（式） | 機械評価可能な等式・不等式（§2.1） |
| 検証クエリ / コード参照 | 実際に実行される検証の所在 |
| 周期 | 評価頻度（§3.2） |
| 差分許容 | 許容される既知差分とその根拠（§3.2） |
| オーナー | 差異発生時に一次対応する責任者 / チーム |

-   **Rule 710.2.6（設計レビュー連動）**: 新しい保存則量（新しい課金単位・新しいポイント種別・新しい在庫区分）を導入する設計レビューでは、**不変量カタログへの追加を必須チェック項目**とする（MUST）。量だけ増えて不変量が増えない PR は差し戻す。

### §2.3. 代表的な不変量パターン

-   **Rule 710.2.7（パターン適用）**: 以下の代表パターンを出発点として用いる（SHOULD）。新規発明より、枯れた会計原則の移植を優先せよ:

| パターン | 不変量の形 | 適用例 |
|:--------|:----------|:------|
| 複式簿記（balanced ledger） | クレジット合計 == デビット合計（常にゼロ和） | 金銭・ポイント・クレジットの移動全般 |
| 計数保存 | 入力件数 == 出力件数 + 失敗件数 + スキップ件数 | パイプライン・ETL・イベント処理（`engineering/700` §2.2 のデータ版） |
| ストック・フロー一致 | 期末残高 == 期首残高 + 流入 − 流出 | 在庫・残高・ポイント失効 |
| ゼロ和移動 | 振替元の減少 == 振替先の増加 | 口座間振替・倉庫間移動・テナント間付け替え |
| 原本・複製一致 | SSOT の集約値 == 複製（キャッシュ / 検索 index / 分析基盤）の集約値 | `engineering/000` SSOT の継続検証 |
| 外部突合 | 自システムの記録 == 外部プロバイダ（決済・銀行・倉庫）の記録 | 決済プロバイダ精算・銀行明細・3PL 在庫 |

## §3. 定常リコンシリエーションジョブ (Continuous Reconciliation Jobs)

> リコンシリエーションは「信頼するが、検証する」の実装である。突合の不在は障害として現れず、**無検証期間**として静かに進行する。

### §3.1. 一回性検証の禁止 — 定常ジョブ化

-   **Rule 710.3.1（定常ジョブ義務）**: 不変量の検証は、リリース時・移行時の一回性検証で終わらせず、**スケジュール実行される定常ジョブ**として運用しなければならない（MUST）。整合性は「一度確認した状態」ではなく「継続的に再確認される性質」である。移行イベント時の一回性突合は `engineering/700` §3.7 を正本とし、移行完了後は本ファイルの定常ジョブへ引き継ぐ。
-   **Rule 710.3.2（突合ジョブの計数契約）**: 突合ジョブ自体も機械呼出ジョブであり、`engineering/700` §2 の失敗計数契約（JobRunSummary・3値 outcome・canonical サマリ行）に従う（MUST）。「突合ジョブが落ちていたことに誰も気づかない」は二重の盲点である。
-   **判定基準**: 「この不変量が最後に検証されたのはいつか？」に、任意の不変量についてシステムが即答できるか。

### §3.2. 周期・対象範囲・差分許容の設計

-   **Rule 710.3.3（周期のリスク連動）**: 検証周期は量のリスクと変化速度に応じて設計する（MUST）。金銭・課金に関わる不変量は**最低でも日次**で評価する（SHOULD）。周期の根拠（なぜこの頻度で十分か）はカタログ（§2.2）に記録する。
-   **Rule 710.3.4（増分 + 全量の二層）**: 対象範囲は **増分検証（直近ウィンドウ）を高頻度 + 全量検証（full scan）を低頻度**の二層で設計する（SHOULD）。増分のみでは過去データの静かな破損（手動操作・バグ修正の副作用）を検出できない。
-   **Rule 710.3.5（差分許容の明文化）**: 既知の正当な差分（丸め・タイムゾーン・為替評価差）を許容する場合、**許容幅と根拠を不変量カタログに明文化**し、ADR で承認する（MUST）。コード内のマジックナンバーとしての「だいたい一致」は禁止する（MUST NOT）。

### §3.3. Multi-System 間突合

-   **Rule 710.3.6（システム間突合義務）**: 保存則量が複数システムに複製・伝搬される場合、**システム境界ごとに突合点を設置**する（MUST）。典型的な突合経路:
    -   DB（正本）↔ キャッシュ / 検索 index
    -   DB ↔ 外部 API / 決済プロバイダ（自レコード ↔ プロバイダ精算レポート）
    -   OLTP ↔ 分析基盤（イベント件数・金額集計の一致）
    -   メータリング収集 ↔ 請求明細（`product/300` の請求定義に対する検証）
-   **Rule 710.3.7（外部プロバイダ突合）**: 決済プロバイダ・銀行・外部倉庫など**自分が管理しないシステム**との突合は、相手方の公式レポート（精算ファイル・明細 API）を入力とし、自システムの記録と機械照合する（MUST）。「プロバイダのダッシュボードを目視」は突合とみなさない。
-   **判定基準**: 保存則量が通過するシステム境界を列挙し、突合点のない境界が 1 つでもあれば、そこが次の不整合の発生源である。

### §3.4. タイミング差と締め境界

-   **Rule 710.3.8（締め境界の定義）**: 突合は**締め境界（cutoff）**を明示して行う（MUST）。処理中（in-flight）のレコードをタイミング差で「差異」と誤判定する突合は、偽陽性でアラートを麻痺させる。境界の取り方（スナップショット時刻・イベント時刻 vs 記帳時刻）はカタログに記録する。
-   **Rule 710.3.9（in-flight の明示計上）**: 締め時点で未確定のレコードは、差異でも一致でもなく **`in_flight` として独立に計数**する（SHOULD）。in-flight の滞留時間が閾値を超えたものだけを差異候補へ昇格させる。

### §3.5. 差異の修復（Remediation）規律

-   **Rule 710.3.10（修復もジョブ）**: 検出された差異の修復は、アドホックな手動 SQL ではなく、**dry-run・計数契約・監査ログを備えた修復ジョブ**として実行する（MUST）。実行規律（dry-run・チャンク・kill switch）は `engineering/700` §3 に従う。
-   **Rule 710.3.11（修復後の再突合）**: 修復の完了判定は、**同一不変量の再評価が green になること**をもって行う（MUST）。「修復スクリプトが正常終了した」ことを完了とみなしてはならない。
-   **Rule 710.3.12（修復経路の一本化）**: 金銭・課金データの修復は §5 の逆仕訳経由に一本化する（MUST）。修復のためであっても確定エントリの上書きを許可しない（MUST NOT）。

## §4. リコンシリエーション 3 メトリクス（Stripe Ledger 型）(The Three Reconciliation Metrics)

> Stripe の Ledger 基盤は、リコンシリエーションの健全性を Clearing / Timeliness / Completeness の 3 メトリクスで観測し、差異の「説明可能性」を運用指標とした。本セクションはこの整理を言語・スタック非依存の規律として移植する。

### §4.1. Clearing — 中間勘定の期待残高ゼロ

-   **Rule 710.4.1（clearing 検証）**: 資金・在庫・クレジットのフローが通過する**中間勘定（clearing account / 仮勘定 / 引当中）は、定常状態で期待残高ゼロ（または明示された期待値）に収束する**ことを検証する（MUST）。中間勘定に滞留する残高は「どの段階でフローが詰まっているか」を示す最良のシグナルである。
-   **実装指針**: フローの各段階を勘定として明示し（複式簿記パターン、§2.3）、段階ごとの残高をメトリクス化する。「最終結果だけ合っている」検証は、途中段階の詰まりを隠す。
-   **先行例**: Uber の精算・会計基盤は、注文 → 決済 → 精算のフローを段階単位の勘定として扱い、大規模な突合を段階ごとに分割して実行する。

### §4.2. Timeliness — 期限内検証率

-   **Rule 710.4.2（timeliness SLO）**: 各レコード / イベントが**発生から一定期限内に検証完了する割合**を計測する（MUST）。例: 「イベント発生から 4 日以内に 99.99% を検証完了」。期限と割合は量のリスクに応じて設計し、SLO として `operations/400` の運用に載せる。
-   **実装指針**: 未検証レコードの経過時間分布（aging）を可視化し、期限接近・期限超過を段階的にエスカレーションする（SHOULD）。
-   **判定基準**: 「いま発生した不整合に、最悪何日後に気づくか？」に数値で即答できなければ、timeliness は計測されていない。

### §4.3. Completeness — 上流全レコード到達の統計的検知

-   **Rule 710.4.3（completeness 検知）**: 上流（イベント発生源・プロバイダ）の全レコードが検証対象の台帳・基盤へ**到達したこと自体**を検知する（MUST）。届いたものだけを突合する設計は、「そもそも届いていないレコード」を原理的に見逃す。
-   **実装指針**: 件数の上流 / 下流照合、シーケンス番号・連番の欠落検知、到達件数の統計的予測（曜日・時間帯別の期待レンジ）との乖離検知を組み合わせる（SHOULD）。

### §4.4. 説明可能性 % の SLO 化

-   **Rule 710.4.4（説明可能性 SLO）**: 検出された差異は **`explained`（既知原因に分類済み）と `unexplained`（未説明）に分類**し、**説明可能性 %（explained / total）を SLO 化**する（MUST）。「差異ゼロ」を SLO・目標にしてはならない（MUST NOT）— 差異ゼロ目標は、差異の隠蔽・許容幅の無断拡大という最悪のインセンティブを生む。
-   **Rule 710.4.5（未説明差異のみ事故）**: インシデント扱いするのは**未説明差異**（および説明済み差異の異常な増加傾向）のみとする（MUST）。説明済み差異は分類コード付きで計上し、傾向監視の対象とする。対応手順は `operations/500` を正本とする。
-   **Rule 710.4.6（未説明の滞留期限）**: 未説明差異には**調査期限（例: 検出から N 営業日）**を設け、期限超過の未説明差異の件数・金額をメトリクス化する（MUST）。「未説明のまま放置された差異」は本ファイルにおける最重要の劣化指標である。
-   **判定基準**: 「最も古い未説明差異は、何日前からいくら未説明のままか？」に即答できる計器があるか。なければ Rule 710.4.6 は実装されていない。

## §5. 追記専用（Append-Only）と逆仕訳 (Append-Only & Reversal Entries)

> 複式簿記の総勘定元帳は数世紀にわたり「追記 + 逆仕訳」で運用されてきた。上書き禁止は新しい制約ではなく、最も枯れた会計統制のソフトウェアへの移植である。

-   **Rule 710.5.1（append-only 義務）**: 金銭・課金・ポイントの記録テーブルは**追記専用（append-only）**とし、確定済みエントリへの UPDATE / DELETE による修正を禁止する（MUST NOT）。上書き可能な金銭記録は、不整合の原因調査を不可能にする。
-   **Rule 710.5.2（逆仕訳による訂正）**: 誤った確定エントリの訂正は、**逆仕訳（reversal entry）+ 正しい訂正エントリの追記**で行う（MUST）。訂正エントリには元エントリへの参照と訂正理由コードを必須とする。これにより不変量（§2.3 複式簿記パターン）は訂正後も成立し続ける。
-   **Rule 710.5.3（手動補正の二段レビュー）**: 運用上の手動補正（manual adjustment）は、**起票者と承認者を分離した二段レビュー（maker-checker）+ 監査ログ記録**を必須とする（MUST）。監査ログの基盤・保持要件は `security/100` を正本とする。単独実行可能な手動補正経路を残してはならない（MUST NOT）。
-   **Rule 710.5.4（補正の突合対象化）**: 手動補正それ自体も保存則量のフローであり、§3 の定常突合対象に含める（MUST）。「補正テーブルだけ突合対象外」は抜け道になる。
-   **Rule 710.5.5（訂正理由タクソノミ）**: 訂正理由コードは低カーディナリティの安定 enum として管理し、訂正の件数・金額を理由別にメトリクス化する（SHOULD）。特定理由の急増は上流バグ・運用劣化の早期シグナルである。
-   **判定基準**: 「この残高がなぜこの値なのか」を、エントリの履歴（追記列）だけから再構成できるか。できなければどこかに上書きが存在する。

## §6. 二重集計防止 (Double-Counting Prevention)

-   **Rule 710.6.1（冪等基盤への委譲）**: 集計ジョブの冪等キー・watermark・チェックポイントの設計は `engineering/700` §3.1–§3.2 を正本とする。本ファイルは**整合観点での検証義務**を追加する: 集計ジョブの再実行・重複起動が発生しても、集計結果が二重計上されないことを**不変量として定常検証**する（MUST）。
-   **Rule 710.6.2（重複検知の計数）**: 入力イベントの重複（at-least-once 配信・リトライ由来）は、排除するだけでなく**検知件数として計数・メトリクス化**する（SHOULD）。重複率の急変は上流の障害・リトライ嵐の早期シグナルである。
-   **Rule 710.6.3（一意性の構造的保証）**: 二重集計の防止をアプリケーションロジックのみに依存させず、**ストレージ層の一意制約（冪等キー・イベント ID）**で構造的に保証する（MUST）。制約違反の発生件数も Rule 710.6.2 と同様に観測する。
-   **Rule 710.6.4（再導出可能性）**: 保存された集計値は原本イベントから**再導出可能**であることを維持し、再導出値と保存集計値の一致を §3 の定常突合対象に含める（SHOULD）。
-   **判定基準**: 「この集計ジョブを今すぐもう一度実行しても、請求額は 1 円も変わらないか？」に Yes と答えられなければ、二重集計リスクが存在する。

## §7. Drift 検知 (Drift Detection)

-   **Rule 710.7.1（drift の定量基準）**: 等式が成立していても進行しうる劣化 — **分布変化（平均・分位点の移動）・スキュー（特定キーへの偏り）・相関喪失（例: 注文数と決済数の相関崩れ）** — を、定量基準（閾値・許容レンジ）付きで監視する（SHOULD）。
-   **Rule 710.7.2（ai/100 との連携）**: 分布監視・データ品質 6 次元の計測手法は `ai/100` を正本とし、本ファイルは**保存則量への適用**（どの量のどの drift が請求・在庫の事故に直結するかの優先順位付け）のみを定義する。
-   **Rule 710.7.3（閾値の見直し記録）**: drift の閾値・許容レンジは事業の季節性・成長に合わせて定期的に見直し、変更は根拠付きで記録する（SHOULD）。無断の閾値緩和は Rule 710.3.5 の許容幅と同様に禁止する（MUST NOT）。
-   **判定基準**: 「不変量はすべて green なのに、請求額が先月から 30% 減っている」に気づける監視があるか。等式検証と drift 検知は相互補完であり、片方では足りない。

## §8. テスト義務 (Testing Obligations)

> テスト層の定義・テストダブル等の総論は `quality/000_qa_testing.md` を正本とする。本セクションは**整合・突合に固有のテスト義務のみ**を定義する。

-   **Rule 710.8.1（不変量のプロパティテスト）**: 不変量は、**任意の正当な操作列を適用した後でも成立する**ことをプロパティベーステストで検証する（MUST）。例: ランダムな入金・出金・訂正の列を生成し、各ステップ後にクレジット合計 == デビット合計を表明する。
-   **Rule 710.8.2（突合ジョブ自体のテスト）**: 突合ジョブは、**既知の差分を意図的に注入したデータセットに対して、その差分を検出・分類できる**ことをテストで検証する（MUST）。差異を検出できない突合ジョブは「偽の安心」を量産する観測装置であり、存在しないより有害である。
-   **Rule 710.8.3（逆仕訳の往復テスト）**: 逆仕訳（§5.2）について、**訂正前 → 逆仕訳 → 再訂正の往復後も不変量と残高が正しい**ことを検証する（MUST）。
-   **Rule 710.8.4（締め境界テスト）**: 締め境界（§3.4）について、in-flight レコードが差異と誤判定されないこと、締め後に確定したレコードが次回突合で拾われることを検証する（SHOULD）。
-   **Rule 710.8.5（カタログ網羅の検証）**: 不変量カタログ（§2.2）の全エントリが、実際にスケジュール登録された定常ジョブを持つことを CI または定期チェックで検証する（SHOULD）。「カタログにあるが誰も評価していない不変量」を構造的に防ぐ。

## §9. 多角観点 (Multi-Perspective Review)

### §9.1. 可観測性

-   **Rule 710.9.1（差異メトリクス）**: 差異件数・差異金額（絶対値）・説明可能性 %（§4.4）・未説明差異の滞留時間（§4.6）を、突合ジョブのログとは別に**メトリクスとして計上**する（MUST）。分類コードは低カーディナリティの安定 enum とする（`engineering/700` §2.6 と同一規約）。
-   **実装指針**: ダッシュボード（§10.3）は不変量単位でドリルダウン可能にし、差異の発生箇所（どの不変量・どの境界）へ最短で到達できる導線を持たせる（SHOULD）。

### §9.2. FinOps

-   **Rule 710.9.2（突合コストの統制）**: 全量突合（§3.2）のスキャン・転送コストは事前に概算し、増分検証との周期バランスで統制する（SHOULD）。突合のための全件スキャンが分析基盤の請求の主因になる事態は、増分化・サンプリング・集約値照合の優先で回避する。総論は `operations/600` を参照。

### §9.3. プライバシー

-   **Rule 710.9.3（突合ログ内 PII 統制）**: 突合結果・差異サンプルに含まれる PII（氏名・口座・カード参照）は、**マスキング・トークン化・参照化（ID のみ保持）**のいずれかを適用する（MUST）。差異調査ログは長期保持されがちな「影のデータストア」であり、保持期間を明示する。詳細は `security/000` §7 を正本とする。

## §10. 実装スニペット (Implementation Snippets)

> 以下はすべて**参考実装**（e.g. SQL / 擬似コード / YAML）であり、言語・スタック非依存の規律（§2–§4）の代表例として示す。自スタックの慣用形に翻訳して用いること。

### §10.1. 不変量チェックの SQL 例（§2.3 複式簿記 / ストック・フロー / 計数保存）

```sql
-- INV-LEDGER-001: クレジット合計 == デビット合計（常にゼロ和）
-- 差異行が 1 行でも返れば違反。締め境界（§3.4）を as_of で固定する。
SELECT
  account_id,
  SUM(CASE WHEN side = 'credit' THEN amount ELSE 0 END) AS credit_total,
  SUM(CASE WHEN side = 'debit'  THEN amount ELSE 0 END) AS debit_total
FROM ledger_entries
WHERE entry_time < :as_of            -- 締め境界: in-flight を除外
GROUP BY account_id                  -- §2.1 粒度の二層: エンティティ単位で評価
HAVING SUM(CASE WHEN side = 'credit' THEN amount ELSE -amount END) <> 0;

-- INV-STOCK-001: 期末残高 == 期首残高 + 入庫 − 出庫（ストック・フロー一致）
SELECT s.sku_id, s.closing_qty, o.opening_qty, f.inbound_qty, f.outbound_qty
FROM stock_snapshots s
JOIN stock_snapshots o ON o.sku_id = s.sku_id AND o.as_of = :period_start
JOIN stock_flows    f ON f.sku_id = s.sku_id AND f.period   = :period
WHERE s.as_of = :period_end
  AND s.closing_qty <> o.opening_qty + f.inbound_qty - f.outbound_qty;

-- INV-PIPE-001: 入力件数 == 出力件数 + 失敗件数 + スキップ件数（計数保存）
SELECT b.batch_id, b.input_count, p.output_count, p.failed_count, p.skipped_count
FROM ingest_batches b
JOIN pipeline_results p ON p.batch_id = b.batch_id
WHERE b.ingested_at < :as_of
  AND b.input_count <> p.output_count + p.failed_count + p.skipped_count;
```

### §10.2. 定常突合ジョブの擬似コード（§3 / §4.4）

```text
job reconcile(invariant, as_of):                    # 700 §2 計数契約に従うジョブ
  left  = evaluate(invariant.source_query,  as_of)  # 経路 A（例: 自システム台帳）
  right = evaluate(invariant.target_query,  as_of)  # 経路 B（例: プロバイダ精算）
  diffs = compare(left, right, key = invariant.join_key)

  for d in diffs:
    if within_tolerance(d, invariant.tolerance):    # §3.2 明文化された許容幅のみ
      count(d, as = "explained", reason = "tolerance")
    elif matches_known_cause(d):                    # 既知原因分類（締め差・為替等）
      count(d, as = "explained", reason = cause_code(d))
    elif is_in_flight(d, as_of):                    # §3.4 in-flight は独立計数
      count(d, as = "in_flight")
    else:
      count(d, as = "unexplained")                  # §4.5 これのみ事故候補
      persist_for_investigation(d, deadline = N_business_days)
      # 修復は §3.5: 逆仕訳ベースの修復ジョブ + 同一不変量の再評価で完了判定

  emit_metrics(explained, unexplained, in_flight, amounts)
  emit_summary_line()                               # 700 §2.5 canonical サマリ行
  alert if unexplained > 0 or overdue_investigations > 0
```

## §11. アンチパターン集 (Anti-Pattern Catalog)

| # | アンチパターン | 違反ルール | 帰結 |
|:--|:-------------|:----------|:-----|
| 1 | 移行時に一度突合しただけで恒久放置（定常ジョブなし） | 710.3.1 | 移行後に混入した不整合が決算・請求で発覚する |

| 3 | 突合をテスト / staging 環境のみで実施し本番に未設置 | 710.3.1 | 本番固有のデータ・タイミング起因の差異が検出されない |
| 4 | 未説明差異を分類も期限もなく放置 | 710.4.4–6 | 説明可能性が劣化し、本物の事故が雑音に埋もれる |
| 5 | 上書き（UPDATE / DELETE）可能な金銭テーブル | 710.5.1 | 監査不能・訂正履歴の消滅・不変量の検証不能 |

| 7 | 不変量なしの新しい課金単位・ポイント種別をリリース | 710.2.1, 710.2.5 | 正しさの定義がないまま金銭量が本番で増殖する |

| 15 | 集計の二重計上防止をアプリロジックだけに依存 | 710.6.3 | 再実行・競合で二重計上し、下流の請求まで汚染する |

## §12. 成熟度モデル L1–L5 (Maturity Model)

| Level | 状態 | 特徴 |
|:------|:-----|:-----|
| **L1: Unverified** | 整合性は信仰 | 不変量の明文化なし。不整合はユーザー問い合わせ・決算で発覚。金銭テーブルが上書き可能 |
| **L2: Spot-Checked** | 一回性の確認のみ | 移行・リリース時に突合した実績はあるが定常ジョブがない。差異対応は属人 |
| **L3: Reconciled** | 定常突合が稼働 | 不変量カタログ + 定常突合ジョブ + append-only / 逆仕訳を実装。差異が分類・計数される |
| **L4: Measured** | 3 メトリクスで運用 | Clearing / Timeliness / Completeness + 説明可能性 % SLO が稼働。未説明差異に調査期限がある |
| **L5: Self-Correcting** | 検証が設計に還流 | 差異の根本原因分析が不変量・許容幅・上流設計の改善に還流。差異注入テストが CI で常時実行される |

-   **Rule 710.12.1（最低ライン）**: 金銭・課金を扱う本番システムは **L3 以上**を必須とする（MUST）。請求金額が外部顧客へ到達するシステムは **L4 相当の運用**を満たしてから拡大する（SHOULD）。
