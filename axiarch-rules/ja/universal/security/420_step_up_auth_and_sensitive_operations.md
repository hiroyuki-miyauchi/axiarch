# 66. ステップアップ認証・重要操作保護 (Step-Up Authentication & Sensitive Operations)

> [!CAUTION]
> **このファイルは Universal Rule（不変ルール）です。「憲法改正」の明示的指示がない限り編集禁止。**
> 改定日: 2026-06-09

> [!IMPORTANT]
> **Level 1 Priority: Absolute Compliance**
> 重要操作（決済・権限変更・個人情報変更・削除・エクスポート・管理操作）の保護は、利便性・開発速度・収益性のいずれよりも優先されます。
> **本ファイルは `000_security_privacy.md §6.2（ステップアップ認証）・§6（セッション管理）・§4.2（MFA）・§3.3（ITDR）` の深掘り版です。**
> 親ファイルとの矛盾が生じた場合は、より厳格な側を採用してください。

> [!CAUTION]
> **Primary Directive（主要方針）**
> 「認証は『誰か』を一度確認する行為ではなく、『重要な瞬間ごとに、適切な確度で、適切な主体であること』を継続的に確認する行為である。」
> セッションの存在は重要操作の許可を意味しない。重要操作のたびに、操作の重大性に見合った保証レベル（assurance level）と認証鮮度（freshness）をサーバ側で検証せよ。
> **優先順位**: Security（資産・データ保護） > Compliance（規制遵守） > UX（摩擦最小化） > DX（実装容易性）。

# I. 基本原則とアシュアランスモデル（§1-§3）

---

## §1. 基本原則

### Rule 66.001: セッション存在 ≠ 操作許可
- **Law**: 有効なセッションの存在は「ログイン状態」を示すに過ぎず、**重要操作の認可を意味しない**。重要操作のたびに、操作の重大性に応じた認証保証レベル（AAL: Authenticator Assurance Level）と認証鮮度（freshness）をサーバ側で検証する。
- **Action**:
  1. 重要操作の認可判定を、認証時に発行したトークンの保有のみに依存させない。
  2. 「いつ・どの強度で・どの要素で」認証されたかを表すメタデータ（後述 §2 の `acr`/`amr`/`auth_time`）を操作時に再評価する。
- **Cross-Reference**: §4（ステップアップ）, §18（サーバ側強制）

### Rule 66.002: 鮮度（Freshness）の原則
- **Law**: 重要操作は「直近の認証」を要求する。古い認証（数時間〜数日前のログイン）では、セッションが盗まれていた場合に重要操作を許してしまう。操作ごとに許容する**最大認証経過時間（max_age）**を定義する。
- **推奨 max_age 基準値**:

| 操作ティア | 操作例 | 推奨 max_age |
|:---|:---|:---|
| **Tier 1: 閲覧** | データ参照 | セッション有効期間内（再認証不要） |
| **Tier 2: 変更** | プロフィール更新 | ≤ 24時間 |
| **Tier 3: 機微変更** | メール/電話/パスワード変更、MFA設定変更 | ≤ 5分（直近の再認証必須） |
| **Tier 4: 金銭・権限** | 決済、ロール変更、API キー発行 | ≤ 5分 + フィッシング耐性要素 |
| **Tier 5: 破壊的** | アカウント削除、全データパージ、一括エクスポート | ≤ 5分 + 二重確認 + 通知 |

- **Note**: 上表は親ファイル `000_security_privacy.md §6.2` の Tiered Security Protocol を操作鮮度の観点で具体化したもの。実値はリスクアペタイトに応じて調整可だが、Tier 3 以上で「無期限に再認証不要」とする設計は禁止。

### Rule 66.003: フィッシング耐性の優先
- **Law**: Tier 4 以上の重要操作では、フィッシング耐性のある要素（**Passkey/FIDO2/WebAuthn、ハードウェアキー**）での再認証を**最優先**とする。SMS OTP を Tier 4 以上の唯一の要素とすることは**禁止**（SIM スワップ・SS7 脆弱性のため。§14 参照）。
- **Cross-Reference**: `000_security_privacy.md §4.2`, `400_authentication_and_passkeys.md`（Passkey 詳細）

## §2. OIDC によるアシュアランスの表現（acr / amr / auth_time / max_age）

### Rule 66.010: 標準クレームによる認証コンテキストの表現
- **Law**: 認証の強度・要素・時刻を、独自実装ではなく **OIDC 標準クレーム**で表現・検証する。
- **主要クレーム**:

| クレーム | 意味 | 用途 |
|:---|:---|:---|
| `acr` (Authentication Context Class Reference) | 認証の保証レベル（例: `urn:mace:incommon:iap:silver`、`phr`=phishing-resistant、独自値も可） | 操作に必要な最低保証レベルの判定 |
| `amr` (Authentication Methods References) | 使用された認証手段（`pwd`, `otp`, `mfa`, `hwk`, `swk`, `fido`, `face`, `fpt` 等） | 要素種別の検証（例: フィッシング耐性要素か） |
| `auth_time` | 実際にユーザー認証が行われた時刻（UNIX 時刻） | 鮮度（freshness）判定 |
| `max_age` | 認可リクエストでクライアントが要求する最大認証経過秒数 | 古い認証時の強制再認証トリガー |

- **Action**:
  1. **要求側**: 重要操作の前に、`max_age` と必要な `acr_values` を付けて再認可リクエストを送る。
  2. **検証側**: ID トークンの `auth_time` が `now - max_age` より新しいこと、`acr`/`amr` が要求保証レベルを満たすことをサーバ側で検証する。
  3. `max_age=0` は「常に再認証」を意味する。Tier 5 では `prompt=login`（または `prompt=login` 相当）で強制再プロンプトを併用。

```typescript
// ✅ 再認証要求（クライアント → 認可サーバ）: 重要操作前に max_age と acr を指定
function buildStepUpAuthUrl(returnTo: string): string {
  const params = new URLSearchParams({
    client_id: process.env.OIDC_CLIENT_ID!,
    redirect_uri: process.env.OIDC_REDIRECT_URI!,
    response_type: 'code',
    scope: 'openid',
    // 直近 300 秒以内の認証でなければ再認証を強制
    max_age: '300',
    // フィッシング耐性レベルを要求（IdP の定義に合わせる）
    acr_values: 'phr',
    // 重要操作では明示的な再プロンプトを併用（任意）
    prompt: 'login',
    // CSRF 対策
    state: generateState(returnTo),
    nonce: crypto.randomUUID(),
  });
  return `${process.env.OIDC_AUTH_ENDPOINT}?${params}`;
}
```

```typescript
// ✅ サーバ側検証: 鮮度・保証レベルを操作時に再評価
import type { JWTPayload } from 'jose';

const PHISHING_RESISTANT_AMR = new Set(['hwk', 'fido', 'pkc']); // 実装/IdPに合わせ調整

function assertStepUpSatisfied(
  claims: JWTPayload & { auth_time?: number; acr?: string; amr?: string[] },
  opts: { maxAgeSec: number; requirePhishingResistant: boolean },
): void {
  const now = Math.floor(Date.now() / 1000);
  if (typeof claims.auth_time !== 'number') {
    throw new StepUpRequiredError('auth_time missing');
  }
  // 鮮度（freshness）検証
  if (now - claims.auth_time > opts.maxAgeSec) {
    throw new StepUpRequiredError('reauthentication required (stale auth_time)');
  }
  // フィッシング耐性要素の検証
  if (opts.requirePhishingResistant) {
    const amr = claims.amr ?? [];
    if (!amr.some((m) => PHISHING_RESISTANT_AMR.has(m))) {
      throw new StepUpRequiredError('phishing-resistant factor required');
    }
  }
}
```

- **Anti-Pattern**: `acr`/`amr`/`auth_time` を ID トークンから読まず、アプリ独自の「最後にログインした時刻」フラグのみで鮮度判定する（IdP の真正な認証イベントと乖離し、改ざん・stale 化のリスク）。
- **Cross-Reference**: `410_federated_identity_and_oauth.md`（OIDC/OAuth 詳細）

## §3. AAL（Authenticator Assurance Level）マッピング

### Rule 66.020: NIST SP 800-63B AAL と操作ティアの対応
- **Law**: 操作の重大性に必要な AAL を定義し、満たさないセッションには操作を許可しない。

| AAL | 要件 | 対応操作ティア |
|:---|:---|:---|
| **AAL1** | 単一要素（パスワード等）。低保証 | Tier 1-2 |
| **AAL2** | 2要素（記憶 + 所持/生体）。多くの重要操作の最低線 | Tier 3-4 |
| **AAL3** | ハードウェア暗号認証子 + 検証者なりすまし耐性（フィッシング耐性必須） | Tier 4-5（高額決済・管理者破壊操作） |

- **Action**: AAL2 以上では再認証の有効期限（reauthentication）を NIST 準拠で管理（AAL2: 最大12時間または30分非アクティブで再認証、AAL3: 最大12時間または15分非アクティブ）。重要操作の `max_age` はこれより短く設定する。
- **Cross-Reference**: §2（max_age）, `000_security_privacy.md §4.9`（パスワードポリシー）

## §4. ステップアップをいつ要求するか

### Rule 66.030: 重要操作の定義（トリガー一覧）
- **Law**: 以下の操作は**重要操作**として分類し、セッションの有効性に関わらずステップアップ（再認証）をサーバ側で強制する。

| カテゴリ | 操作例 | 最低ティア |
|:---|:---|:---|
| **決済・金銭移動** | 課金、送金、出金、払い戻し、支払い方法追加・変更 | Tier 4 |
| **権限・ロール変更** | 管理者昇格、ロール付与/剥奪、メンバー招待（特権） | Tier 4 |
| **認証要素変更** | パスワード変更、MFA 追加/削除、Passkey 登録/削除、リカバリ手段変更 | Tier 3 |
| **連絡先変更** | メールアドレス変更、電話番号変更 | Tier 3 |
| **個人情報変更** | 法的氏名、住所、本人確認情報（KYC）の変更 | Tier 3 |
| **削除・破壊** | アカウント削除、ワークスペース削除、全データパージ | Tier 5 |
| **エクスポート** | 一括データエクスポート、ポータビリティ要求、バックアップダウンロード | Tier 4 |
| **管理操作** | 監査ログ閲覧/削除、暗号鍵操作、本番環境への設定変更 | Tier 4-5 |
| **API/シークレット** | API キー発行/失効、OAuth クライアント作成、Webhook 署名鍵更新 | Tier 4 |
| **デバイス/セッション** | 信頼済みデバイス追加、全セッション一括失効の解除 | Tier 3 |

- **Note**: 「連絡先変更」と「認証要素変更」は ATO の典型的な乗っ取り後操作（被害者を締め出す）であるため、特に厳格に保護する（§28 参照）。

### Rule 66.031: 変更の連鎖防御
- **Law**: メールアドレス変更直後に「旧メールへ通知 + 一定期間のロールバック猶予」を設ける。連絡先・パスワード変更時は**全セッション失効**（§24）と**操作通知**（§21）を併発させ、攻撃者が単一の変更で完全乗っ取りに至る連鎖を断ち切る。

## §5. 再認証（Re-authentication）の実装方式

### Rule 66.040: 再認証の3方式
- **Law**: 再認証は、操作のティアと利用可能な要素に応じて以下から選択する。劣化方向（強→弱）の自動フォールバックは Tier を下げない範囲でのみ許可。

| 方式 | 概要 | 適性 |
|:---|:---|:---|
| **WebAuthn 再認証** | 既登録 Passkey/認証子で `navigator.credentials.get()` を実行し、`userVerification: 'required'` で生体/PIN を要求 | Tier 4-5 の最優先。フィッシング耐性 |
| **TOTP/OTP 再入力** | 既登録の TOTP もしくはワンタイムコードの再入力 | Tier 3-4。WebAuthn 非対応環境のフォールバック |
| **パスワード再入力** | 現在のパスワードの再確認 | Tier 3 の最低線。単独では Tier 4 不可 |

```typescript
// ✅ WebAuthn 再認証（クライアント）: userVerification を required にし、チャレンジはサーバ発行
async function reauthenticateWithWebAuthn(): Promise<PublicKeyCredential> {
  const options = await fetchServerChallenge(); // サーバが challenge/allowCredentials を発行
  const assertion = await navigator.credentials.get({
    publicKey: {
      challenge: base64urlToBuffer(options.challenge),
      allowCredentials: options.allowCredentials,
      userVerification: 'required', // 生体/PIN を必須化（所持＋検証）
      timeout: 60_000,
    },
  });
  return assertion as PublicKeyCredential;
}
```

### Rule 66.041: 再認証チャレンジの単一用途束縛
- **Law**: 再認証のチャレンジ（WebAuthn challenge / OTP）は、**特定の操作 1 件**に束縛する。チャレンジ成功で得る「ステップアップ済み」状態は、操作対象・操作種別・短い有効期間（例: 5分）にスコープする。汎用の「ステップアップ済みフラグ」を立ててセッション全体に適用してはならない（一度の再認証で無関係な重要操作まで通る穴を防ぐ）。

## §6. ステップアップ・トークン／グラント

### Rule 66.050: 短命ステップアップグラントの設計
- **Law**: 再認証成功時に、操作スコープ付きの短命グラント（例: 署名済み JWT または サーバ側セッション内の一時フラグ）を発行する。
- **必須クレーム/属性**:
  - `sub`（主体）, `op`（許可された操作種別）, `target`（対象リソース ID）, `iat`/`exp`（≤ 5分）, `jti`（単回使用・リプレー防止）, `acr`/`amr`（達成保証レベル）。
- **Action**: 重要操作ハンドラはこのグラントを検証し、`jti` を消費済みリストに登録して再利用を拒否する。

```typescript
// ✅ 重要操作ハンドラのサーバ側ガード（疑似コード）
async function requireStepUp(req: Request, op: SensitiveOp, targetId: string): Promise<void> {
  const grant = await verifyStepUpGrant(req); // 署名・exp・acr/amr を検証
  if (grant.op !== op || grant.target !== targetId) {
    throw new StepUpRequiredError('grant scope mismatch');
  }
  if (await isJtiConsumed(grant.jti)) {
    throw new StepUpRequiredError('grant already used'); // リプレー防止
  }
  await consumeJti(grant.jti, grant.exp);
}
```

## §7. 信頼済みデバイス（Remember this device）

### Rule 66.060: 信頼済みデバイスの慎重な扱い
- **Law**: 「このデバイスを信頼する」機能は摩擦を下げるが、デバイス盗難・共有端末で悪用される。以下を満たす場合のみ許可する。
  - 信頼の対象は **Tier 3 以下**に限定。Tier 4-5（金銭・破壊・権限）は信頼済みデバイスでも**毎回ステップアップ必須**。
  - 信頼の有効期限を設定（例: 30日）。期限後は再ステップアップ。
  - 信頼トークンは HttpOnly・Secure・SameSite 属性の専用 Cookie とし、デバイスシグナル（§9）と束縛。
  - ユーザーが「信頼済みデバイス一覧」を確認・個別失効できる UI を提供（§27）。

## §8. リスクシグナルとスコアリング

### Rule 66.070: リスクシグナルの収集
- **Law**: ログイン・重要操作の各イベントでリスクシグナルを収集し、リスクスコアを算出する。
- **主要シグナル**:

| カテゴリ | シグナル例 |
|:---|:---|
| **デバイス** | 新規デバイス、デバイスフィンガープリント変化、改造/ルート化、エミュレータ |
| **ネットワーク** | 新規 IP、IP レピュテーション（Tor/VPN/データセンター）、ASN 変化 |
| **地理** | 新規国/地域、Impossible Travel（地理速度）、高リスク地域 |
| **時間/行動** | 異常時間帯、行動バイオメトリクス（タイピング/操作リズム）の逸脱 |
| **アカウント** | 直近の認証失敗、最近のパスワード/連絡先変更、漏洩クレデンシャル一致 |
| **操作** | 高額・通常と異なる送金先、短時間の連続重要操作 |

### Rule 66.071: 段階的防御（リスクスコア閾値）
- **Law**: リスクスコアの閾値に応じて段階的に防御を強める。低リスクは透過（摩擦ゼロ）、高リスクはブロックする。

| リスク帯 | アクション |
|:---|:---|
| **低** | 透過（追加摩擦なし） |
| **中** | OTP / TOTP によるステップアップ |
| **高** | フィッシング耐性要素（Passkey/ハードウェアキー）必須 |
| **極高** | ブロック + 帯域外通知 + 手動レビュー/ITDR 連携 |

- **Cross-Reference**: `000_security_privacy.md §3.3`（ITDR）, `000_security_privacy.md §6.4`（Impossible Travel）

## §9. デバイスフィンガープリント／ボット検知連携

### Rule 66.080: デバイスシグナルの扱い
- **Law**: デバイスフィンガープリントとボット検知（§参照: `000_security_privacy.md §23`）をリスクスコアの入力として連携する。ただしフィンガープリントは**唯一の認証要素にしてはならない**（偽装可能・プライバシー懸念）。あくまでリスク評価の補助シグナルとする。
- **Action**: フィンガープリント生成・保存はプライバシー原則（§36）に従い、同意・最小化・保持期限を遵守する。

## §10. 継続的アクセス評価（CAEP / Continuous Access Evaluation）

### Rule 66.090: セッション中のリアルタイム再評価
- **Law**: ゼロトラストの「継続的検証」（`000_security_privacy.md §2.1.4`）に従い、セッション発行後もリスク状態の変化を検知して即時に権限を見直す。
- **Action**:
  1. **CAEP / Shared Signals Framework (SSF)**: IdP・リソース間でセキュリティイベント（セッション失効・クレデンシャル変更・デバイスポスチャ低下）を Push 共有し、即時に再認証/失効をトリガー。
  2. ポーリングではなくイベント駆動（Push）を優先し、トークン有効期限まで放置しない。
  3. 高リスクイベント検知時は当該セッションへステップアップ要求または失効を即時適用。
- **Cross-Reference**: §22-§24（セッション管理）, `000_security_privacy.md §3.3`

---

## §11. アダプティブ認証の運用規律

### Rule 66.100: 誤判定（FP/FN）の管理
- **Law**: リスクエンジンの誤検知（正規ユーザーへの過剰摩擦）と見逃しを継続監視し、閾値を調整する。
- **Action**: ステップアップ発火率・成功率・誤検知率・離脱率を計測（§31）。安全側に倒しつつ、UX（§35）を毀損しないバランス点を定期レビュー。

# IV. OTP・ワンタイムリンク（§12-§15）

---

## §12. TOTP（RFC 6238）

### Rule 66.110: TOTP 実装規律
- **Law**: TOTP は RFC 6238 に準拠して実装する。
- **要件**:
  - **アルゴリズム/桁数/周期**: HMAC-SHA-1（互換性のため一般的。新規は SHA-256 も検討）/ 6桁 / 30秒。
  - **時刻ずれ許容**: ±1ステップ（前後30秒）まで。過度な許容窓は総当たりを容易にするため禁止。
  - **シークレット生成**: 暗号論的乱数で十分なエントロピー（≥ 160bit）。
  - **シークレット保管**: 保存時暗号化（KMS）。平文保存禁止。
  - **検証**: 固定時間比較（§13）、レート制限・試行回数制限（§13）。
  - **再利用防止**: 直近に成功した OTP（同一タイムステップ）の再利用を拒否（リプレー防止）。
  - **登録時検証**: 登録フローで TOTP の正常生成をユーザーに 1 回検証させてから有効化。

```typescript
// ✅ TOTP 検証: 固定時間比較 + 直近ステップの再利用拒否
import { timingSafeEqual } from 'node:crypto';

function verifyTotp(secret: Buffer, code: string, opts: { window?: number } = {}): boolean {
  if (!/^\d{6}$/.test(code)) return false; // 形式検証（列挙レスポンスは一定に）
  const window = opts.window ?? 1;
  const step = Math.floor(Date.now() / 1000 / 30);
  for (let i = -window; i <= window; i++) {
    const expected = generateTotp(secret, step + i);
    const a = Buffer.from(expected);
    const b = Buffer.from(code);
    if (a.length === b.length && timingSafeEqual(a, b)) return true; // 固定時間比較
  }
  return false;
}
```

## §13. OTP 共通の実装規律

### Rule 66.120: レート制限・試行回数・列挙防止
- **Law**: OTP 検証エンドポイントは総当たり・列挙の標的になる。以下を必須とする。
  - **試行回数制限**: 同一チャレンジに対する検証試行を上限（例: 5回）でロックし、再発行を要求。
  - **レート制限**: IP・ユーザー・チャレンジ単位の多層レート制限。OTP 発行（送信）側にもレート制限を適用（コスト・スパム防止、§32）。
  - **固定時間比較**: コード比較は `timingSafeEqual` 等で実施。タイミング攻撃を防止。
  - **列挙防止**: 「コードが違う」「ユーザーが存在しない」「OTP 未発行」を区別せず統一エラーを返す。レスポンス時間も一定化。
  - **有効期限**: メール/SMS OTP は短命（例: 5〜10分）。期限切れ後は無効。
  - **単回使用**: 検証成功後は即座に無効化（リプレー防止）。

### Rule 66.121: バックアップコード
- **Law**: MFA/OTP 喪失時のリカバリ用バックアップコードは、ハッシュ化保存（§参照: `000_security_privacy.md §4.9` のパスワードハッシュ規律に準ずる）、単回使用、生成時の 1 回のみ表示、再生成時の旧コード一括失効を強制する。

---

## §14. メールマジックリンク／ワンタイムリンク

### Rule 66.130: ワンタイムリンクの規律
- **Law**: マジックリンク（パスワードレスログイン）・確認リンクは以下を満たす。
  - **有効期限**: 短命（例: 10〜15分）。
  - **単回使用**: 一度使用したら無効化。
  - **同一デバイス/コンテキスト束縛**: リンク発行デバイスと開封デバイスの整合チェック（推奨）。少なくとも開封後にチャレンジ確認コードを併用し、リンク横取り（メール傍受）単独での成立を防ぐ。
  - **トークン形式**: 推測不能な暗号論的乱数トークン。URL に PII を含めない。
  - **プリフェッチ対策**: メールクライアント/セキュリティスキャナのリンクプリフェッチで消費されないよう、GET 単独で副作用を起こさず、明示的な確認アクション（POST）で初めて消費する設計とする。
  - **レート制限・列挙防止**: §13 と同様。

### Rule 66.131: マジックリンクの限界
- **Law**: マジックリンクはメールアカウントの安全性に全面依存する。メールが乗っ取られると全面突破される。重要操作（Tier 4-5）の唯一の要素にしてはならず、フィッシング耐性要素（§3）と併用する。

---

## §15. SMS／音声 OTP の限界と限定利用

### Rule 66.140: SMS/音声 OTP の位置付け
- **Law**: SMS/音声 OTP は **SIM スワップ・SS7 プロトコル脆弱性・フィッシング**により高リスク。以下を厳守する。
  - **Tier 4-5 の唯一要素として使用禁止**（`000_security_privacy.md §4.2` と整合）。
  - 利用する場合も補助要素に留め、フィッシング耐性要素（Passkey）への移行を計画する。
  - SMS OTP **一択**の MFA 設計は**非推奨（Deprecated）**。Passkey/TOTP を第一選択とする。
  - 送信文面に「このコードを誰にも教えないこと」を明記し、ソーシャルエンジニアリング耐性を高める。
- **Anti-Pattern**: 高額決済の確認を SMS OTP のみで行う（§39）。

# V. トランザクション認証・署名（§16-§17）

---

## §16. トランザクション認証（WYSIWYS）

### Rule 66.150: What You See Is What You Sign
- **Law**: 高額・高リスクのトランザクション（送金・支払い・重要設定変更）では、**実際に承認する内容**（金額・送金先・対象）を認証チャレンジに提示し、その内容に束縛した確認を取る（WYSIWYS: What You See Is What You Sign）。汎用の「OK ですか？」ではなく、トランザクション固有のチャレンジとする。
- **Action**:
  1. チャレンジ（OTP メッセージ/プッシュ/WebAuthn の表示文言）に金額・送金先など要点を含める。
  2. サーバ側で、ユーザーが確認したトランザクション内容と実行内容が**完全一致**することを検証（途中改ざんを検知）。
  3. WebAuthn では `clientDataJSON` に紐づくチャレンジへトランザクションハッシュを束縛し、署名対象を明確化。
- **Cross-Reference**: §18（サーバ側強制）, §21（Idempotency）

---

## §17. PSD2 SCA / Dynamic Linking の一般化

### Rule 66.160: 動的リンク（Dynamic Linking）の原則
- **Law**: 欧州 PSD2 の Strong Customer Authentication（SCA）と Dynamic Linking の考え方を、決済に限らず**高リスクトランザクション一般**に適用する。
- **要件（一般化）**:
  - 認証コードは**金額と受取人**（または対象操作）に**動的に紐付く**。
  - 金額・受取人が変われば認証コードは無効化される。
  - 認証情報の機密性・真正性・完全性を保護する。
- **Note**: 規制対象の決済を扱う場合は、`product/300_revenue_monetization.md` の決済規律および各決済プロバイダ（Stripe 等）の SCA/3DS 要件に従う（§38 責任分界点）。

# VI. 重要操作ゲートの実装規律（§18-§21）

---

## §18. サーバ側強制（クライアント判定禁止）

### Rule 66.170: 認可判定はサーバ側でのみ
- **Law**: 重要操作のステップアップ要否・成否の判定は**サーバ側でのみ**行う。クライアント（UI のボタン制御、フロントの条件分岐）での判定は UX 上のヒントに過ぎず、**セキュリティ境界として信頼してはならない**。
- **Anti-Pattern**: フロントエンドで「ステップアップ済みか」を判定し、API 側で再検証しない（§39 筆頭アンチパターン）。
- **Cross-Reference**: `000_security_privacy.md §10.1`（BOLA/BFLA）, §4.5（集約ガード）

---

## §19. 二重確認（Confirmation）

### Rule 66.180: 破壊的操作の明示的確認
- **Law**: Tier 5（削除・パージ）は、ステップアップに加えて**明示的な意図確認**（対象名のタイプ入力など、誤操作を防ぐ高摩擦確認）を要求する。確認はステップアップグラント（§6）と同一トランザクションに束縛する。

---

## §20. 監査ログ（不変）

### Rule 66.190: 重要操作の不変監査ログ
- **Law**: 全重要操作を**不変（追記専用・改ざん検知可能）**な監査ログに記録する。
- **記録項目**: 主体（ユーザー/NHI）, 操作種別, 対象リソース, 実行時刻, 結果（成否）, ステップアップ達成 `acr`/`amr`, リスクスコア, 送信元 IP/デバイス, 相関 ID。
- **PII 規律**: ログに過剰な PII を含めない（`000_security_privacy.md §7.4` マスキング準拠）。
- **Cross-Reference**: `operations/000_internal_tools.md`（管理操作の監査）, `000_security_privacy.md §4.6`

---

## §21. 通知・Idempotency

### Rule 66.200: 操作通知
- **Law**: 重要操作の実行をユーザーに帯域外（メール/プッシュ）で通知する。特に認証要素変更・連絡先変更・新規デバイス・高額決済は**即時通知**し、「心当たりがない場合」の即時失効動線（全セッション失効 §24）を提供する。

### Rule 66.201: Idempotency（冪等性）
- **Law**: 金銭・破壊操作は **Idempotency Key** を必須とし、ネットワーク再送・二重送信での重複実行を防ぐ。サーバ側で同一キーの重複リクエストを安全に重複排除する。
- **Cross-Reference**: `engineering/100_api_integration.md`（API 設計）

---

# VII. セッション管理（§22-§27）

---

## §22. トークン有効期限・リフレッシュローテーション

### Rule 66.210: 短命アクセストークン + リフレッシュローテーション
- **Law**: アクセストークンは短命とし、リフレッシュトークンは**ローテーション**する（`000_security_privacy.md §6.1` の基準を踏襲）。

| トークン種別 | 推奨有効期限 | 管理画面向け |
|:---|:---|:---|
| **Access Token** | ≤ 1時間 | ≤ 15分 |
| **Refresh Token** | 7〜30日（ローテーション必須） | ≤ 7日 |
| **Step-Up Grant** | ≤ 5分（単回使用） | ≤ 5分 |
| **Session Cookie** | ブラウザセッション | ブラウザセッション |

- **Refresh Token Rotation**: リフレッシュのたびに新トークンを発行し旧を無効化。**再利用検知**（無効化済みリフレッシュトークンの使用）時は、当該トークンファミリ全体を即時失効しユーザーに通知（盗難の兆候）。

---

## §23. アイドル／絶対タイムアウト

### Rule 66.220: タイムアウト基準値
- **Law**: セッションには**アイドルタイムアウト**（無操作）と**絶対タイムアウト**（発行からの最大寿命）の双方を設定する。「無期限セッション」は**禁止**。

| 区分 | アイドルタイムアウト | 絶対タイムアウト |
|:---|:---|:---|
| **一般ユーザー** | 30分〜数時間（用途依存） | ≤ 30日 |
| **管理者/特権** | ≤ 15分 | ≤ 12時間 |
| **金融/高機微** | ≤ 5〜15分 | ≤ 8時間 |

- **Note**: AAL2/AAL3 の再認証要件（§3）と整合させる。

---

## §24. セッション無効化・全セッション失効

### Rule 66.230: イベント駆動の失効
- **Law**: 以下のイベントで関連セッションを**サーバ側で即時失効**する（クライアントのトークン削除のみは不十分。`000_security_privacy.md §6.5` 準拠）。
  - パスワード変更/リセット → **全セッション失効**（操作元セッションは任意で維持可）。
  - MFA/Passkey 変更、連絡先変更 → 全セッション失効を強く推奨。
  - アカウント停止/削除 → 全セッション即時失効。
  - 侵害検知（ATO/ITDR）→ 全セッション失効 + 再認証要求。
- **実装**: Token Revocation List（または短命トークン + サーバ側セッションストアの失効フラグ）で検証時に照合。CAEP（§10）で分散リソースへ Push。
- **Panic Button（Kill Switch）**: 全セッション一括失効手順を常時最新に維持（`000_security_privacy.md §6.7`）。

---

## §25. セッション固定攻撃対策

### Rule 66.240: 認証境界でのセッション ID 再生成
- **Law**: ログイン成功時・権限昇格時・ステップアップ成功時に**セッション ID（および固定識別子）を再生成（regenerate）**する。認証前に発行された識別子を認証後も使い回すこと（Session Fixation）を禁止する。

---

## §26. Cookie 属性

### Rule 66.250: セッション Cookie の必須属性
- **Law**: セッション/認証 Cookie には以下を必須設定する。
  - `HttpOnly`: JS からの読取り不可（XSS によるトークン窃取緩和）。
  - `Secure`: HTTPS のみ送信。
  - `SameSite=Lax`（推奨）または `Strict`: CSRF 緩和（`000_security_privacy.md §10.8` 準拠）。
  - `__Host-` プレフィックス: パス `/`・Secure・ドメイン非指定で、サブドメインからの上書きを防止（可能な場合）。
  - 適切な `Path`・`Max-Age`/`Expires`（§23 のタイムアウトと整合）。

---

## §27. デバイス／セッション管理 UI

### Rule 66.260: ユーザー可視のセッション管理
- **Law**: ユーザーが**アクティブセッション一覧**（デバイス・場所・最終アクティブ時刻）と**信頼済みデバイス一覧**を確認し、個別/一括で失効できる UI を提供する。
- **同時セッションポリシー**: 同時ログイン上限を設定し、超過時は最古を失効。管理者はより厳格に（同時1〜2、`000_security_privacy.md §6.3`）。

---

# VIII. アカウントテイクオーバー（ATO）・MFA Fatigue（§28-§30）

---

## §28. ATO 検知と対応

### Rule 66.270: ATO シグナルと自動対応
- **Law**: アカウントテイクオーバーの兆候を検知し、自動で防御する。
- **シグナル**: 異常地理/デバイスからのログイン、ログイン直後の連絡先/パスワード/MFA 変更、漏洩クレデンシャル一致、Impossible Travel、短時間の高額操作。
- **自動対応**: 高リスク時はステップアップ強制 → セッション失効 → 帯域外通知 → 必要に応じ一時凍結 + ITDR 連携（`000_security_privacy.md §3.3`）。
- **乗っ取り後操作の防御**: ログイン直後の連絡先/認証要素変更には追加のステップアップとクールダウン（変更反映前の待機・ロールバック猶予、§4.31 相当）を課す。

---

## §29. MFA Fatigue／プッシュ爆撃対策

### Rule 66.280: プッシュ承認の濫用防止
- **Law**: 短時間に大量のプッシュ承認要求を送る MFA Fatigue（プッシュ爆撃）攻撃に対し、構造的に防御する（`000_security_privacy.md §4.2` を深掘り）。
- **Action**:
  - **Number Matching（番号照合）**: 単純な「承認/拒否」ではなく、画面に表示された番号を入力させる方式を採用。
  - **コンテキスト表示**: プッシュにログイン元アプリ・場所・IP を表示。
  - **レート制限**: 短時間の連続プッシュ要求を抑制し、閾値超過でプッシュを一時停止 + ユーザー通知。
  - **拒否シグナル**: ユーザーが「拒否」した場合をリスクシグナル化し、当該試行をブロック・調査。

---

## §30. クレデンシャルスタッフィング連携

### Rule 66.290: 漏洩クレデンシャル検知との連携
- **Law**: 漏洩パスワード照合（Have I Been Pwned 等、`000_security_privacy.md §4.9`）の結果をリスクスコアへ反映し、一致時は強制パスワード変更 + ステップアップを要求する。
- **Cross-Reference**: `000_security_privacy.md §6.6`（ブルートフォース防止）

---

# IX. 多角的観点（可観測性・FinOps・UX・スケール・プライバシー・a11y）（§31-§37）

---

## §31. 可観測性（Observability）

### Rule 66.300: ステップアップ／認証メトリクス
- **Law**: 以下を計測・アラートし、攻撃と UX 劣化の双方を可視化する。
  - ステップアップ**発火率**（操作種別別）、**成功/失敗率**、平均所要時間。
  - OTP 検証失敗率、ロックアウト発生数、MFA Fatigue 検知数。
  - リスクスコア分布、段階防御の発動分布、ATO 検知/誤検知率。
  - 異常: ステップアップ失敗の急増、特定 IP/デバイスからの集中、地理偏在。
- **Cross-Reference**: `000_security_privacy.md §26`（セキュリティ可観測性）

---

## §32. FinOps

### Rule 66.310: 認証コストの最適化
- **Law**: OTP 送信（SMS/音声/メール）・リスクエンジン（IDaaS の MAU/評価課金）はコスト要因。安全性を損なわずコストを最適化する。
- **Action**:
  - SMS OTP のコスト・到達性・セキュリティ劣位を踏まえ、Passkey/TOTP（送信コストゼロ）へ誘導。
  - リスクエンジンは低リスク帯を透過させ、評価/チャレンジ回数を必要十分に抑制。
  - OTP 送信レート制限（§13）はコストとスパム防止を兼ねる。
- **Cross-Reference**: `operations/600_cloud_finops.md`

---

## §33. パフォーマンス／レイテンシ

### Rule 66.320: ステップアップ経路の性能
- **Law**: リスク評価・ステップアップ検証はホットパスに入る。レイテンシ予算を定め、外部リスクエンジン/IdP 障害時のフェイルセーフ（安全側=操作拒否、可用性とのトレードオフを明文化）を設計する。

---

## §34. スケーラビリティ

### Rule 66.330: 失効・グラントの分散整合
- **Law**: セッション失効・ステップアップグラント・`jti` 消費は分散環境で一貫検証できる必要がある。短命トークン + 集中失効ストア（または CAEP Push）で整合性とスケールを両立する。

---

## §35. UX（摩擦と安全のバランス）

### Rule 66.340: 必要な時だけ摩擦を
- **Law**: ステップアップは**重要操作・高リスク時に限定**し、低リスク操作には摩擦を課さない（アダプティブ）。過剰な摩擦はユーザーの危険な回避行動（MFA 無効化等）を誘発する。
- **Action**: 再認証後は操作を中断なく継続（コンテキスト保持）。失敗時は次に取るべき行動を明確に案内（列挙防止とのバランスに留意）。

---

## §36. プライバシー

### Rule 66.350: リスクシグナルのプライバシー保護
- **Law**: デバイスフィンガープリント・位置・行動バイオメトリクス等のリスクシグナルは PII/機微情報を含み得る。収集目的の限定・最小化・保持期限・同意（適用法域に応じ）を遵守する（`000_security_privacy.md §7`）。
- **Cross-Reference**: `100_data_governance.md`

---

## §37. アクセシビリティ（a11y）

### Rule 66.360: 再認証・OTP の a11y
- **Law**: ステップアップ/OTP フローは WCAG 準拠とし、特定能力に依存しない複数手段を提供する。
- **Action**:
  - OTP/再認証画面のスクリーンリーダー対応、十分な制限時間（短すぎる有効期限は時間延長の代替手段を提供）。
  - 生体（Face/指紋）が使えないユーザー向けの代替要素（PIN・セキュリティキー）を必ず用意。
  - OTP 入力フィールドの `autocomplete="one-time-code"`・適切なラベル付け。
  - 番号照合（§29）は視覚のみに依存しない提示を検討。

---

# X. 責任分界点（§38）

---

## §38. IDaaS／決済プロバイダとの責任境界

### Rule 66.370: 何を委ね、何を自前で守るか
- **Law**: ステップアップ・リスク評価・セッション管理の責務を、IDaaS・決済プロバイダと明確に分界する。

| 領域 | IDaaS / 外部プロバイダに委ねる | 自前ロジックで保証する |
|:---|:---|:---|
| **認証/MFA/Passkey** | 認証フロー、要素管理、`acr`/`amr` 発行 | `acr`/`amr`/`auth_time` の**検証**と操作への適用 |
| **リスクエンジン** | シグナル収集・スコアリング（利用時） | 閾値設計、段階防御の発動、業務固有シグナル |
| **セッション** | トークン発行/ローテーション（利用時） | 重要操作ゲート、失効トリガー、監査ログ |
| **決済 SCA/3DS** | 決済プロバイダ（Stripe 等）が SCA/3DS を実施 | トランザクション内容の WYSIWYS 検証、Idempotency、通知 |

- **Rule**: 外部に委ねても**最終的な認可判定とサーバ側強制（§18）の責任は自社にある**。プロバイダのリスク判定を鵜呑みにせず、業務固有の重要操作ゲートを必ず自前で重畳する。
- **Cross-Reference**: `engineering/500_firebase_gcp.md`（Firebase Auth/Identity Platform）, `product/300_revenue_monetization.md`（決済）

# XI. アンチパターン集（§39）

---

## §39. アンチパターン

### Rule 66.380: 禁止・非推奨パターン一覧
- **Law**: 以下は重大な脆弱性につながるため**禁止または非推奨**とする。

| # | アンチパターン | 問題 | 正しい対応 |
|:--|:---|:---|:---|
| 1 | クライアント側だけで重要操作をガード | API 直叩きで突破 | サーバ側で必ず再検証（§18） |
| 2 | 高額決済を SMS OTP のみで確認 | SIM スワップ/SS7 で突破 | フィッシング耐性要素 + WYSIWYS（§3, §16） |
| 3 | セッションを無期限化（タイムアウトなし） | 盗難セッションが永続 | アイドル/絶対タイムアウト（§23） |
| 4 | パスワード変更後も他セッションが残存 | 乗っ取り後も攻撃者が居座る | 全セッション失効（§24） |
| 5 | OTP に試行回数/レート制限なし | 総当たり・列挙が可能 | 試行制限 + レート制限 + 固定時間比較（§13） |
| 6 | MFA Fatigue 無対策（単純承認プッシュ） | プッシュ爆撃で誤承認 | Number Matching + 抑制（§29） |
| 7 | ステップアップ済みフラグをセッション全体に適用 | 一度の再認証で無関係操作も通る | 操作・対象に束縛した単一用途グラント（§41, §6） |
| 8 | `auth_time`/`acr` を見ず独自フラグで鮮度判定 | 改ざん・stale 化 | OIDC 標準クレームを検証（§2） |
| 9 | マジックリンクを Tier 4-5 の唯一要素にする | メール乗っ取りで全面突破 | フィッシング耐性要素併用（§14.131） |
| 10 | 認証後にセッション ID を再生成しない | Session Fixation | 認証境界で regenerate（§25） |
| 11 | Cookie に HttpOnly/Secure/SameSite 未設定 | XSS/CSRF でトークン窃取 | 必須属性 + `__Host-`（§26） |
| 12 | リフレッシュトークンを無回転で長命運用 | 盗難時に長期悪用 | ローテーション + 再利用検知失効（§22） |
| 13 | OTP 検証で文字列 `===` 比較 | タイミング攻撃 | `timingSafeEqual`（§12, §13） |
| 14 | 列挙可能なエラー（「コード違い」vs「未発行」） | アカウント/状態列挙 | 統一エラー + 一定レスポンス時間（§13） |
| 15 | 重要操作の通知なし | 不正に気づけない | 帯域外即時通知 + 失効動線（§21） |
| 16 | 金銭操作に Idempotency なし | 二重課金/二重送金 | Idempotency Key 必須（§21） |
| 17 | WYSIWYS なし（汎用「OK？」確認） | 内容すり替えに気づけない | トランザクション内容を提示・束縛（§16） |
| 18 | フィンガープリントを単独の認証要素化 | 偽装で突破 + プライバシー侵害 | 補助シグナルに限定（§9） |
| 19 | 連絡先変更直後に即時反映・通知なし | 乗っ取り後に被害者を締め出し | 旧連絡先通知 + 猶予/ロールバック（§4.31, §28） |
| 20 | 全操作に一律で強いステップアップ | 過剰摩擦→ユーザーが MFA 無効化 | リスク/ティアに応じたアダプティブ（§35） |
| 21 | バックアップコードを平文保存・再利用可 | 漏洩で恒久バイパス | ハッシュ保存・単回・再生成失効（§13.121） |
| 22 | 管理操作を信頼済みデバイスで素通し | デバイス盗難で特権操作 | Tier 4-5 は毎回ステップアップ（§7） |

# XII. 成熟度モデル（§40）

---

## §40. 成熟度モデル（L1-L5）

### Rule 66.390: ステップアップ・重要操作保護の成熟度
- **Law**: 自組織の現在地を評価し、段階的に L5 を目指す。

| レベル | 状態 | 代表的特徴 |
|:---|:---|:---|
| **L1: Initial** | 場当たり的 | 重要操作の保護が一部のみ。クライアント判定依存。SMS OTP 中心。セッション無期限の箇所が残る |
| **L2: Managed** | 基本整備 | 重要操作を分類しサーバ側でステップアップ。TOTP/OTP のレート制限・固定時間比較。基本的タイムアウト |
| **L3: Defined** | 標準化 | OIDC `acr`/`amr`/`max_age` で鮮度・保証レベルを統一管理。リフレッシュローテーション + 全セッション失効。WYSIWYS。監査ログ整備 |
| **L4: Quantified** | 計測駆動 | リスクベース段階防御。発火率/失敗/誤検知をメトリクス化。MFA Fatigue 対策（Number Matching）。Passkey へ移行進行 |
| **L5: Optimizing** | 継続最適化 | CAEP/SSF による継続的検証。フィッシング耐性デフォルト。アダプティブで摩擦最小化。ATO 自動対応 + ITDR 完全連携。閾値の継続自動調整 |
